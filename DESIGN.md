# morca: design

November 1, 2026 · targets stable Mojo 1.2.0

This turns [VISION.md](VISION.md) into a buildable plan. It covers phase 1 in detail, sketches phases 2 to 6 and keyed partitions, and proposes answers to the vision's open questions. Everything marked *verified* was compiled and run on Mojo 1.2.0; every other claim about what Mojo accepts is checked in the PR that first needs it, and this file is corrected when one turns out wrong.

## What morca builds on

| Tin | What morca uses | State today |
|---|---|---|
| dista | `Runtime[*Ts]` in local mode (forked head and workers) per run; `Task`, `ObjectRef`, `Seq`; registry hash; the timeline | Phases 1 to 3 merged: actors, checkpoints, shuffles |
| iceberg | `FilesystemCatalog`, `Table.scan().use_snapshot(id)`, `AppendFiles`, `prepare_commit` with `extra_summary` and file removals | 0.8.2 |
| parquet, arrow-mlake | Reading TLC files, building `RecordBatch`es | 0.11.x, 0.2.0 |
| objectstore | HTTP GET for downloads, S3 for the warehouse and logs | ABI 4 |
| postgres | morca's state: `Connection`, `Transaction`, prepared statements; `scripts/with-pg-server.sh` for tests | 0.3.2 |
| flare_mlake | The HTTP API and UI (phase 3) | 0.13.0 |

morca adds no FFI of its own.

## Programming model

A step is a top-level `def`. Like a dista task, it's declared once with its input and output types written out, and a pipeline is the list of its steps:

```mojo
from dista import Seq
from morca import Ctx, Step, Mapped, Gather, Pipeline, Month, morca_main

@fieldwise_init
struct RawFile(Movable, Copyable):
    var month: Month
    var path: String

@fieldwise_init
struct Loaded(Movable, Copyable):
    var month: Month
    var snapshot_id: Int64

def download(mut ctx: Ctx, month: Month) raises -> RawFile: ...
def load(mut ctx: Ctx, raw: RawFile) raises -> Loaded: ...
def compact(mut ctx: Ctx, loaded: Seq[Loaded]) raises -> Int64: ...

comptime Download = Step["download", Month, RawFile, download, Mapped]
comptime Load = Step["load", RawFile, Loaded, load, Mapped, after=Download]
comptime Compact = Step["compact", Seq[Loaded], Int64, compact, Gather, after=Load]

comptime Taxi = Pipeline["taxi", Download, Load, Compact]

def main() raises:
    morca_main[Taxi]()
```

- **An edge is a type check.** `after=Download` means `load` takes `Download`'s output. A `Mapped` step after a `Mapped` step takes one partition's output; a `Gather` step takes a `Seq` of all of them. `Step` asserts at compile time that its input type matches what its `after` produces, so `Load` declared with `Int` as input doesn't compile. This is the vision's first principle. *Verified:* `Step` takes `after` as a keyword parameter of a `StepLike` type, and its `check` compares reflected type names in `comptime assert`s, which fail the build with the assert's message. `tests/compile_fail/` holds one pipeline per rule.
- **Partitions from the start, kept simple.** A run is over a list of partition keys (months in phase 1). A `Mapped` step runs once per key; a `Gather` step once per run. The first step of a pipeline takes the key itself. Phase 2 adds partition definitions, schedules and backfills on top of the same two kinds.
- **Steps are listed in run order.** A step comes after the step it follows, so the declared order is a valid order and there's no sort to do. `Pipeline.check` asserts it, along with unique names and that a step's `after` is the pipeline's own step of that name (compared by function, so another step with the same name doesn't pass). *Verified.*
- **One input per step, as in dista.** Several upstreams arrive later as `after=(A, B)` and a struct input; the taxi load doesn't need it.
- **Step outputs are small values**: paths, snapshot IDs, counts. They're stored in Postgres through dista's codec, so a resumed run hands a step the same input the first attempt had. The data itself goes in tables.
- **`Ctx`** is what a step gets besides its input: the run and step IDs, the partition key, a logger, the catalog, and the run's dista runtime. Its table methods are where pinning and lineage happen (below).
- **The registry hash** of a pipeline is a hash over its steps' linkage names, their kinds and edges, their declared datasets (`replaces=` hashed as writes, so switching to it keeps the hash), a step's `version=` when one is set, and the dista registry hash. A run records it, so the code a run ran is known, and resuming with a different binary is refused.

### Heavy work inside a step

A step runs in the run's driver process and calls dista for anything distributed. dista's `Runtime[*Ts]` is parameterised by its tasks, so the pipeline names them, as a keyword parameter after its steps:

```mojo
comptime TaxiTasks = Tasks[ReadMonth, WriteFile]
comptime Taxi = Pipeline["taxi", Download, Load, Compact, tasks=TaxiTasks]

def load(mut ctx: Ctx, raw: RawFile) raises -> Loaded:
    ref rt = ctx.runtime[TaxiTasks]()
    var r = rt.remote[ReadMonth](raw.month)
```

- **`Ctx` stays one type.** It holds the runtime by address, and `ctx.runtime[T]()` returns it as `T.RT` (`Runtime[*Ts]`) after checking that `T`'s tasks are the run's. The check compares task linkage names, because every `Runtime` reflects to the same type name. *Verified.*
- **One runtime per run**, started before the first step and kept to the end: in local mode it forks a head and `MORCA_WORKERS` workers (default 4); with `DISTA_HEAD` set it joins that cluster. It starts before morca opens a database connection or its heartbeat thread, so the forked processes inherit neither. A pipeline without `tasks=` starts none.
- **The same binary is dista's head and worker.** With `DISTA_ROLE` set, `morca_main` hands the process to dista before reading its arguments, so `DISTA_ROLE=worker DISTA_HEAD=... taxi` is a worker. *Verified* by hand: a head, three workers and a driver, each a separate process of the fanout example.
- **The tasks are part of the DAG**: their names are in `describe` and in the registry hash.

## Processes

**The pipeline binary is the unit.** Every pipeline is its own binary, built from its one Mojo file, and the binary is also the run's dista driver and workers. `morca_main` gives it a command line:

| Command | What it does |
|---|---|
| `taxi describe` | The DAG as JSON: steps, kinds, edges, types, registry hash |
| `taxi run --partitions 2024-01..2024-12` | Starts a run, prints its ID, runs it to the end |
| `taxi resume <run>` | Continues a run at its unfinished steps |
| `taxi status [<run>]` | Runs, or one run's steps and attempts |
| `taxi fires [<count>] [--after <time>]` | From phase 2: the schedule's next fires, each with the partition it fills |

Without `MORCA_DATABASE_URL`, `run` records its run in memory (`MemoryStore`, run 0) on the same code path as a recorded one, and nothing outlives the process. Exit codes: 0 for a run that succeeded, 1 for one with a step that didn't, 2 for a usage error, 3 for anything else (the database, a run that can't be resumed).

With `MORCA_DATABASE_URL=sqlite:<path>` (`sqlite:///var/orca/runs.db` for an absolute path; `sqlite://<path>` is the same as `sqlite:<path>`), `run`, `resume` and `status` keep their runs in that SQLite file (`morca.sqlite_store.SqliteStore`), with the same rules as Postgres; see "Single-node morca on SQLite" below. The scheduler, the UI and morca's other commands need Postgres, and refuse a SQLite URL.

Connection settings come from the environment: `MORCA_DATABASE_URL`, `MORCA_WAREHOUSE`, `MORCA_LOGS` (a directory or `s3://`), and dista's own variables.

**The scheduler, from phase 2, is a separate generic `morca` binary** that depends on morca's core, postgres and flare, and on no pipeline. It knows a pipeline by its `describe` output and starts runs by executing the pipeline binary: a subprocess locally, a Kubernetes Job in phase 5. That answers the vision's "where step code runs": the scheduler never links a pipeline's dependencies, which is the same split dista is making between its generic head and the user's driver. It also means a scheduler restart doesn't kill running runs; they're separate processes writing to Postgres themselves. In a container, though, the runs die with the scheduler's container; with `MORCA_OVERLAP=on` a deploy instead starts the new image's scheduler beside the old one, which hands over the lead and drains its runs before it exits ([docs/overlap.md](docs/overlap.md)).

## State in Postgres

One schema, `morca`, created and migrated by the binary at start-up (a `schema_version` table, migrations as SQL strings in the source):

| Table | Holds |
|---|---|
| `pipelines` | name, registry hash, `describe` JSON, first and last seen |
| `runs` | id, pipeline, registry hash, partitions, trigger (manual, schedule, backfill, sensor), status, created, started, ended, heartbeat, and an error when no step's says why it ended |
| `steps` | run, step, partition key (null for a gather step), status, the encoded input, the encoded output |
| `attempts` | step row, attempt number, status, started, ended, error message, log location, host |
| `reads` | attempt, table, snapshot ID: what each attempt read |
| `commits` | attempt, table, snapshot ID: what each attempt committed |

`reads` and `commits` are the lineage table the vision puts in phase 4; they're written from phase 1 because resuming needs them. Phase 4 adds dataset names, the queries and the UI over them.

- **Statuses.** A run is `queued`, `running`, `succeeded`, `failed`, `deferred` (a step asked to wait) or `cancelled`. A step is `pending`, `running`, `succeeded`, `failed`, `deferred` or `skipped` (its upstream didn't succeed).
- **One writer per run.** A process that runs a run is its `owner` (`host:pid`) and holds it by its heartbeat: a thread with a connection of its own (threads.mojo's `TypedPool`) updates `runs.heartbeat` five times per `MORCA_STALE_SECONDS` (default 30), and `resume` refuses a run whose heartbeat is younger than that. A run whose process died has a stale heartbeat and can be resumed; a run that ended clears its heartbeat, so a failed run can be resumed at once. Every attempt's first transaction also checks that this process still owns the run, so a process that lost its run to a resume (it was paused, or the database was unreachable) stops at its next step instead of racing the new owner. No advisory locks for this, so a pooled connection is fine; migrations take a transaction-scoped one. *Verified* by `tests/kill.sh`. **Commits to Iceberg are fenced.** The ownership check at each attempt leaves the whole of a step in between, and a process whose heartbeat went stale while it was alive (the database unreachable for longer than the stale limit, a paused VM) may meanwhile have lost its run to a restart that reruns the step. So right before each commit to a table, `morca.tables` checks (`Ctx.fence`) that this process still owns the run and that its heartbeat is younger than half the stale limit; otherwise the attempt fails without committing. No other process can have claimed the run then, nor claim it during the commit unless the commit takes longer than the other half. A database that can't be reached is waited for until that half has passed, then the commit is refused too. *Verified* by `tests/test_tables.mojo` (`test_a_lost_run_doesnt_commit`, `test_a_stale_heartbeat_doesnt_commit`).
- **Each state change is one transaction.** Starting an attempt inserts it and marks the step running; finishing it records the output, reads and commits, and marks the step. A kill between the two leaves an attempt `running` with a stale heartbeat, which resume marks `failed` before retrying.
- **The pipeline binary sees a `RunStore`, not SQL** (#82). `morca.store`'s `Store` is the executor's view (attempts, skips, pinned reads, reads and commits through `Ctx`'s `Recorder`); `RunStore` adds the rest of what `morca.cli` asks: `migrate`, `register`, `scheduled_hash`, `version`, `create_run`, `claim`, `ran_version`, `interrupt`, `prior`, `run_info`, `runs`, `steps`, and for the run it owns `own`, `start_heartbeat`/`stop_heartbeat`, `finish_run` and `cancel_requested`. `morca.state.PgStore` implements it over `State`; the heartbeat is the store's (`morca.heartbeat.Heartbeat[B]`, one thread beating a `Beater` on a connection of its own). The scheduler and the UI stay on `State`'s SQL: claims with `SKIP LOCKED`, the listings and the lineage queries are queries, and a trait over them would grow a method per page (`docs/future-directions.md`).

## Single-node morca on SQLite

`SqliteStore` (#82, over sqlite-mojo 0.3.5) is the second `RunStore` with a disk behind it, for a laptop, one VM or CI: resumable runs and nothing to operate.

- **The same tables, without the schema.** `pipelines`, `pipeline_versions`, `runs`, `steps`, `attempts`, `reads`, `commits`, with Postgres's column names, holding what a pipeline binary writes (none of the scheduler's columns). A step's input and output are hex text; times are Unix seconds to the millisecond. It has migrations of its own, applied in `BEGIN IMMEDIATE`, as Postgres's are under an advisory lock. Run numbers are `AUTOINCREMENT`, never given out twice in one file, since commits are recognised by them. A new file starts again at run 1, so a warehouse must not outlive its runs' file (as with a Postgres database).
- **One writer at a time.** WAL mode: readers (`status`, `sqlite3`) and the writer don't block each other, but writers take turns. Each change is one `BEGIN IMMEDIATE` transaction, which takes the write lock up front; a writer that finds it taken waits a second (`busy_timeout`) and then fails, and the owned run's writes are retried on the file opened again for `MORCA_DB_RETRY_SECONDS`, as `PgStore` reconnects. A claim is one guarded `UPDATE`, so two resumes racing for a run can't both win, and every attempt checks ownership in its own transaction. Several runs' processes on one machine take turns with the lock for microseconds per write; hundreds of them at once would wait on it.
- **One machine.** SQLite's locks don't hold over NFS and most network file systems, so the file must be on a local disk, and the runs' processes on that machine: no Kubernetes or EC2 runner over it.
- **No scheduler.** The scheduler claims queued runs with `SELECT ... FOR UPDATE SKIP LOCKED`, counts live runs under a row lock and computes what's done in SQL of its own (`DONE_SQL`); the UI's listings and the lineage queries are Postgres SQL too. They stay on Postgres (docs/future-directions.md); a single-node scheduler would be a dialect shim over that SQL (`SKIP LOCKED` becomes `BEGIN IMMEDIATE`, since there is one writer anyway), not more trait.
- **`synchronous = FULL`**: a commit is on disk before it returns, so a power loss as well as a kill keeps every recorded attempt.
- *Verified* by `tests/store_suite.mojo` on a file (`test-store`), and by `tests/chaos.sh` over a file (`test-chaos-sqlite`): kills, resumes racing to claim and flaky steps as on Postgres, with Postgres's restarts replaced by another writer holding the file's lock for up to 1.9 s, past the busy timeout, so the run's writes fail and are retried on the file opened again.

## Snapshots: pinned reads, recognisable commits

This is what makes reruns safe (the vision's fourth principle).

- **`ctx.scan(table)`** returns a `TableScan` pinned to a snapshot. On a step's first attempt that's the table's current snapshot, recorded in `reads`. A retry or resume of the same step gets the snapshot the first attempt read, so it sees the same data whatever was committed in between.
- **`ctx.append(table)`** and **`ctx.commit(table, ...)`** add summary properties to the snapshot they commit: `morca.pipeline`, `orca.run`, `morca.step`, `orca.partition`, `orca.attempt`, `orca.run-token` (the run's random token), `orca.code` (the registry hash), `orca.partitions` (the keys the commit holds: its partition for a mapped step, the run's for a gather step; from phase 4) and `orca.reads` (the `table@snapshot` pairs the attempt read). iceberg's `prepare_append` and `prepare_commit` already take `extra_summary`.
- **A commit is recognised on retry.** If an attempt committed and was killed before Postgres heard of it, the retry looks through the table's snapshots for one whose `orca.run`, `morca.step` and `orca.partition` match, and treats it as the step's commit instead of appending again. So a crash between the commit and the record doesn't load a month twice. Every snapshot the table still has is looked at. A run's number alone doesn't tell its commits from those of a run that had the number before it (one that a restore of morca's database lost, or one of another database over the same warehouse), so each run also has a random token, a UUID version 7 (`orca.runs.token`, `Store.run_token`; `orca.uuidv7()` makes it, since Postgres has `uuidv7()` only from 18), its commits carry it as `orca.run-token`, and a snapshot with another run's token isn't recognised; a snapshot or a run without a token, from before them, is told by the number as before (#292). *Verified* by `tests/test_run_token.mojo`.
- **A step that commits to several tables** records each; one recognised commit doesn't imply the others happened, so each is checked. A step that commits to one table more than once numbers its commits (`orca.commit`), and each is recognised by its number.
- **Reads and commits are recorded as they happen**, each by its own write from the attempt (`Ctx.recorder`, which writes through the run's `Store`), not when the attempt ends, so a process killed between its commit and its end still leaves both on record.
- **An in-memory run** (no database) has run 0, and a second in one process -1, and so on: it pins reads across its own retries and resumes within its process, but recognises no commits, since every process's in-memory runs share those numbers.
- **A table read while it had no snapshot** stays empty for the step, even if a commit lands before a retry.
- **Writers racing on one table.** Two commits on the same metadata version both back out (iceberg's filesystem catalog deletes both files), so `append` and `commit` reload and retry after a random wait that grows with each try, up to 8 times; retrying at once, writers kept clashing in step. *Verified* by `tests/concurrent_commits.sh`: six processes appending to a new table at once, five times, all commit.
- **Files written on workers.** A step whose dista tasks produce the rows can have them write the data files too and send back only the entries, so the step commits metadata instead of receiving the rows over IPC and writing them on one core. On the worker, `load_dataset` gets the table (workers have `MORCA_WAREHOUSE` like the step) and `write_files` or a `FileWriter` writes uncommitted files and returns `DataFiles`, a dista `Codec` over iceberg's versioned `DataFile.encode`; a task result that is a struct of a `DataFiles` and plain fields is encoded by dista's reflection. The step commits them with `append_files(ctx, table, files)`, which is `append` without the writing: the same `writes=` check, summary properties and `find_commit` recognition, so a retry never commits them twice. A step checks `find_commit` before sending the tasks, so a retry doesn't have them write the files again; files written by an attempt that died before its commit are left unreferenced in `data/`, as with an interrupted `append`. The codec lives in morca rather than iceberg because iceberg doesn't depend on dista and morca depends on both. *Verified* by `tests/test_append_files.mojo`: files written in tasks on two workers, a resumed run and a retried step each leave one snapshot per partition, and a retry without the check writes files again that aren't committed.
- **Replacing partitions.** A new run of a key (`morca backfill --rerun`, `morca rerun`) is a new run: `find_commit` recognises only this run's commits, so a step that appends appends again, and the key's rows are there twice. A step that recomputes a key's rows declares the dataset in `replaces=` (it counts as written; `describe` lists it under both). Its `append` and `append_files` to it, or `replace_partitions` / `replace_partition_files` to any table, commit through the same `_found`, fence and summary path, but each commit first plans, against the snapshot it builds on, the live data and delete files in the partitions its new files land in (under the current spec; manifests whose partition summaries can't hold them aren't read) that this run didn't commit — a file is this run's when the snapshot that added it has this run's `morca.pipeline` and `orca.run` (or, in memory, this attempt committed it). If there are any, the commit is an `overwrite` that removes them; otherwise an `append`. So the run's first commit to a partition replaces what earlier runs left, its later commits find only its own files and append, and a retried attempt recognises its commits by number as before and never overwrites twice. Each summary has `orca.replaced-files` and `orca.replaced-records` (with iceberg's `deleted-data-files`, `deleted-records`). The partition is owned by the run: a file in it that another writer added after the run's first commit to the table means two runs are replacing (or writing) it at once, and the commit raises, committing nothing, rather than remove the other's files and leave each with half a partition. Of two racing runs, the one whose first commit came last finishes with all its rows and the other fails; rerunning it once the first has finished replaces the partition again. A clash on the metadata version replans on the reloaded snapshot, never replaying the file list an earlier try planned (mojo-census GAPS #29). No new rows replace nothing; an unpartitioned table is one partition. The granularity is the table's partition: a step whose key is finer than the partitions it writes (hourly keys into a daily partition) would have one key's rerun remove its siblings' rows, so it should append. *Verified* by `tests/test_replace.mojo` (a rerun keeps one copy, a retry after a partial attempt gives the uninterrupted result, two interleaved runs keep one run's rows, append mode unchanged, unpartitioned tables) and `tests/replace_concurrent.sh` (five processes replacing one month at once, five rounds: one complete run's rows each time, the others failing with the reason).
- **Stale removals are refused.** `commit(ctx, table, operation, FileChanges)` checks, on its first try and on each retry after a clash, that the snapshot it prepared removes every file `removed` names (iceberg's `deleted-data-files` plus `removed-delete-files`). A file that isn't in the current snapshot was removed or replaced by another writer since the caller read it; iceberg's `prepare_commit` raises only when none is current, so a partly stale overwrite used to commit and keep both writers' rows (GAPS #29). Now nothing is committed and the attempt fails, so the step's retry plans again. iceberg.mojo#83 asks for the same check in `prepare_commit`. Removing files still reads every manifest of the table (`_carry_or_rewrite`, GAPS #28): a replace that removes files pays that once per commit that removes any, which is the run's first commit to a partition.
- **A rerun that would append again is refused.** `morca backfill --rerun` of keys that are done, and `morca rerun <run> <step>`, are refused for a pipeline whose steps (from that step on, for `morca rerun`) write a dataset they don't declare in `replaces=` (`appending_writes`, from the registration's `describe`; a registration from before `replaces=` appends to all it writes), naming each step and dataset, unless `--allow-append` (the UI's refusal page has a button that posts it, `allow_append=1`; the backfill preview takes `&allow_append=1`). A backfill without `--rerun` skips done keys, so it's never refused. *Verified* by `tests/datasets.sh`.
- **Where it lives.** `morca.tables` (`scan`, `append`, `append_files`, `commit`) imports iceberg, so only pipelines with tables build it. Its tests run in the `data` environment, with iceberg and its siblings from source as in dista. *Verified* by `tests/test_tables.mojo`.

## Failure and resume

- **A failed step** fails its run once its retries are used up. Its downstream steps are `skipped`; other partitions' steps that don't depend on it carry on, so one bad month doesn't stop the other eleven.
- **Retries** are per step: `retries=2` in the `Step` declaration, at once or after `backoff_seconds=30` doubling with each retry (the process sleeps; the heartbeat keeps going). Phase 2 retries a failed *run* with backoff, by resuming it. `ctx.attempt` tells a step which attempt it is. Every attempt is a row in `attempts`, retries and resumes alike.
- **"Not yet" isn't a failure.** A step that can't do its work yet (a month the TLC hasn't published, an API out of requests) raises `defer(seconds, why)`. Its attempt ends `deferred` with `deferred until <time>: why`, spending no retry; its downstream steps are skipped; and the run, if no step failed, ends `deferred` with `retry_at` the latest time its deferred steps asked for (on `morca.civil.now`'s clock, which `MORCA_NOW` fixes). The scheduler starts it again then, whatever its trigger, as it starts a retry, and `runs.deferrals` counts those starts so `run_retries` doesn't. A deferred run's keys are live, so a backfill doesn't queue them again; the UI shows "until <time>" and can resume it at once or cancel it. *Verified* by `tests/defer.sh`.
- **A step that won't end** is bounded by `timeout_seconds=N` on its `Step`. The run's heartbeat thread checks, on each beat, for an attempt of such a step older than N seconds. It fails the attempt and its step ("timed out after N s"), fails the run with that as `runs.error`, writes an audit row and exits the process: a step can't be interrupted on the main thread, so the step's own retries and the run's other partitions wait for the run's retry, which the scheduler makes as for any failed run. Before this, a hung `git clone` held a run, and on EC2 its instances, until `MORCA_RUN_DEADLINE` (a day). A local process the scheduler started whose heartbeat goes stale (wedged, or stopped) is killed before its run is cancelled, failed or started again. *Verified* by `tests/stop.sh`.
- **History is bounded.** Every table `ensure_table` creates (or finds without them) gets `write.metadata.delete-after-commit.enabled=true`, `write.metadata.previous-versions-max=100` and `history.expire.max-snapshot-age-ms` (30 days), and a step can pass its own (`ensure_table(..., properties=)`). Each commit then deletes the metadata files older than the last hundred. Snapshots are expired by the project's `morca_maintain` binary (`morca.maintain`; the `morca` binary doesn't link iceberg): `morca expire <dataset>|--all`, and the scheduler's sweep every `MORCA_EXPIRE_HOURS` (24) of each dataset morca commits to that has a `history.expire.max-snapshot-age-ms`, by that policy. Whatever the policy, `morca.expiry.retained` keeps from Postgres: the snapshots a queued, running, deferred or failed run read (its retries and `resume` scan those), the ones such a run committed (`find_commit` recognises them on a retry), and every snapshot of the last run that committed to the dataset. `morca lineage` and the UI's dataset pages read Postgres, so they still list an expired snapshot and what it was made from and into; the snapshot itself can no longer be read. *Verified* by `tests/expire.sh`.
- **What dista recovers, and what's left to morca.** A dista worker that dies has the tasks it was running sent to another worker, up to `DISTA_TASK_RETRIES` times (default 3). dista doesn't rebuild results lost with a worker (Ray's lineage reconstruction is out of scope there), so a step whose dista work needed one fails, with `result <id> lost: its worker went away`, as does a step whose local runtime has no workers left (`no workers left`). Either failure is an ordinary step error: the step's own retries run it again, and past them the run fails and the scheduler retries the run with backoff, as a new process with a fresh runtime. What makes running a step again safe is already here: its reads are pinned to the first attempt's snapshots, and a commit the earlier attempt made is recognised rather than made twice (see "Snapshots"). A step's own side effects outside its tables must be safe to repeat too.
- **A blip of Postgres doesn't stop a run.** Every write a run's process makes (starting and finishing an attempt, a skip, a read or commit recorded, the run's end) is retried on a new connection, after a quarter of a second doubling to 4 s, for `MORCA_DB_RETRY_SECONDS` (default the stale limit, past which another process may take the run over anyway). A step that worked for an hour and then met a two-second restart is recorded, not redone. The ownership check is the one failure not retried: a run lost to another process, or cancelled, stops at once. Finishing an attempt sets its rows to what they'd be after one try, so a retry after a lost reply is harmless; one after a lost reply to *starting* an attempt leaves the first try's row `running`, which the next resume marks `interrupted`. A server that stays away longer stops the run as before, to be resumed. *Verified* by `tests/db_blip.sh`: the server restarted twice under a toy run, which succeeds with one attempt per step.
- **A local runtime doesn't replace workers.** One runtime serves a run from its first step to its last, and in local mode a worker that dies stays dead, so a step retried in the same run has fewer workers. A run that loses them all fails its next steps quickly instead of hanging, and its retry, a new process, starts with a full set. On a cluster (`DISTA_HEAD` set) Kubernetes restarts the pods. *Verified* by `tests/lost_workers.sh`: with one of four workers killed mid-step the run succeeds with an undisturbed run's total; with all four killed the step fails, its retry fails at once with `no workers left`, and the run, resumed as a new process, succeeds with the same total.
- **Resume** reruns every step that hasn't `succeeded`, in dependency order, with the recorded inputs and pinned reads. Steps that succeeded aren't run again; their outputs are read back from Postgres. A resume after a code change is refused unless `--allow-new-code`, which records the new hash on the attempts it makes.
- **Order within a run.** Steps run in dependency order; independent partitions of a `Mapped` step run one after another in the driver in phase 1, each free to use dista for parallelism inside. Running several partitions' steps at once moved to phase 2, with backfills: in one driver it would need a thread per partition, each with its own database connection, and dista's `Runtime` isn't safe to share between threads. Phase 2 gets the same effect with one run per partition, started `max_runs` at a time, each in its own process.

## Logs

With `MORCA_LOGS` set to a directory, each attempt writes its log to `$MORCA_LOGS/<pipeline>/<run>/<step>/<partition>/<attempt>.log` (`_run` for a gather step) and records the location in `attempts.log`, which `status <run>` shows. The file always exists: morca writes the attempt's start, its end, and its error if it failed; `ctx.log` adds the step's lines, each with a UTC timestamp, and prints them to stdout too. The step's own stdout and stderr aren't captured in phase 1, since steps run in the driver process. A run of a pipeline with tasks writes its dista timeline (Chrome's trace format) beside its logs as `timeline.json`. Since phase 5, `MORCA_LOGS` can be in object storage (`s3://`), where pods don't share a disk; see phase 5's PR 4. *Verified* by `tests/logs.sh`, and over MinIO by `test-lineage-s3`.

## Machine metrics

A run's logs, timeline and task spans say nothing about the machines it ran on. `morca sample` (`morca.sample`; `<binary> sample` in a pipeline binary, which is what the runners start, since every instance and image has it) runs beside each process that does a run's work and appends a JSON line every `MORCA_SAMPLE_SECONDS` (5; the first a fifth of a second after it starts) to `<MORCA_LOGS>/<pipeline>/<run>/metrics/<instance>.jsonl`:

- **CPU:** user, system, iowait and steal as percentages of all cores, and the busiest core.
- **Memory:** total, used, available, page cache, swap, and the resident set of the run's own processes (the process tree it watches, plus, on Linux, processes whose command is the pipeline's binary, which on the ec2 runner live in containers rather than under the script).
- **Disk:** total, used and free per file system holding the temporary directory and dista's spill and store directories, and read and write bytes per second over whole disks.
- **Network:** bytes in and out per second, loopback left out.

Each line carries `v` (1), the Unix time `t`, `dt` since the previous line, the host, the core count and the sampler's own CPU seconds. Readers ignore keys they don't know: the control instance's containers (#96) and CPU counters (#97) will be added as keys of their own, without a new `v`. Linux is read from `/proc` and `statvfs`; macOS, so a local run on a laptop has metrics too, from `host_processor_info`, `host_statistics64`, `sysctl` (memory, swap), `getifaddrs` and `statfs`, with no disk rates (`io` is `null`) and iowait and steal always 0.

Where it runs:

| Runner | Started by | Instance | Ends |
|---|---|---|---|
| local | the scheduler, beside each run's process | `local` | after a last line once the run's process has |
| ec2 | each instance's user data, next to dista; in docker mode as a container with `--pid host` and `/tmp` mounted | `<role>-<instance id>`, beside `cluster/<role>-<instance id>.log` | after a last line once the script makes its `--until` file; the script waits up to 10 s for its first line before starting the work, so even a run shorter than that keeps a sample |
| kube | each pod's command, wrapped in `sh -c` so the sampler runs beside it and signals reach the command | the pod's name | after a last line once the pod's command has |

On ec2 the lines go to a file in `/tmp` that the script's uploader puts under the run's `metrics/` with the instance's log, every `MORCA_CLUSTER_LOG_SECONDS` and once at the end, so a short run's samples are kept and a terminated instance keeps what it had uploaded. On Kubernetes, where run pods don't share the scheduler's `MORCA_LOGS`, the sampler prints its lines to the pod's log prefixed `orca-sample `, and the scheduler moves them to `metrics/<pod>.jsonl`, out of `driver.log`, before it deletes a finished Job: a pod deleted mid-run takes its samples with it, as it takes its log. With `MORCA_LOGS` in object storage, a local sampler stages its file and uploads the whole of it every `MORCA_SAMPLE_UPLOAD_SECONDS` (30) and when it ends.

A sampler never fails a run: it's a process of its own, it exits 0 whatever happens, and a line it can't write is dropped with one message. `MORCA_SAMPLE_SECONDS=0` turns it off on every runner. It checks for its `--until` file and its process four times a second. SIGTERM ends it at once with its lines so far: Mojo's runtime threads would take a signal the main thread blocked, so it can't wait for one. A line is about 500 bytes, so a 1-hour run on 5 instances at 5 s keeps under 2 MB. Its CPU is about 0.4 ms a line: over 60 s at 5 s, 15 ms on Linux (arm64, 0.025% of one core) and 22 ms on an M-series Mac; `tests/sample.sh` asserts under 0.5%. CloudWatch isn't used: detailed and custom metrics cost about $0.30 per metric per month, for instances that live for one run. *Verified* by `tests/sample.sh` (the sampler itself; over MinIO in `test-sample-s3`), `tests/scheduler.sh` (local), `tests/ec2.sh` (a file per instance that lived, and a run shorter than the interval) and `tests/kind.sh` (a file per pod, none in `driver.log`).

### On the run's page

`morca ui` reads a run's samplers' files back (`morca.metrics`; from object storage too, listing the run's `metrics/`) and, under the timeline, draws **Machines**: one SVG, server-rendered like the DAG, with a lane per step (a bar per attempt, from `orca.attempts`) and three strips per instance on the same wall-clock axis: CPU (user and system as an area, iowait above it, steal as a line), memory used and the fullest disk's used space in percent of the instance's, and disk and network rates scaled to the instance's highest. Under it a table gives each instance's peaks: CPU, busiest core, steal, memory and disk (bytes and percent), and rates. The run's JSON has them as `instances[].peaks`, on the ec2 instances' entries (by `<role>-<instance id>`) and on entries of their own for a local run's machine and a Kubernetes run's pods. **Warnings** are stretches where memory was over 90% of the instance's, a disk over 90% full or steal over 20%: bands over the steps lane and the instance's strips, rows in the peaks table, and `peaks.warnings` in the JSON. A running run's page polls `/runs/<id>/metrics` as it polls its steps, until it answers 286. A run without samples renders as before.

The axis is the run's own wall clock rather than dista's timeline's, whose times count from its first task and carry no wall-clock anchor; drawing the samples on the dista lanes needs dista to write that anchor. A page reads at most 50,000 samples per instance (69 hours at 5 s), parsing about 13 µs each, and draws the highest value in each pixel, so a peak isn't averaged away. *Verified* by `tests/test_metrics.mojo` and `tests/ui.sh`.

**What each attempt used** (`morca.usage`; migration 35, #200) is measured by whoever started the run's process, not by a sampler beside it: the scheduler for local and control-placed runs, `morca worker` for its own. Each tick (at most every quarter of a second) one pass over `/proc` (`morca.sample.tree_usage`) gives each such process's tree its resident bytes and CPU seconds (utime + stime, with cutime + cstime, so a child that ended and was waited for stays counted), kept as a `Meter` of at most 1024 marks (neighbours merged as it fills, keeping their maximum and the later total). `reap` uses `wait4`, whose `ru_maxrss` (the largest single process: a lower bound on the tree) and CPU seconds close the meter. Since one process runs every attempt of a run's start, the marks are shared out by time: an attempt's peak is the largest sample while it ran (the next one, for an attempt shorter than a tick), its CPU the meter's at its end less at its start, its peak cores the busiest interval it overlapped; `ru_maxrss` raises an only attempt's peak. The attempts are found by `orca.attempts.host` (`<host>:<pid>`), with times as seconds before the database's `now()`, so a worker's clock needn't agree: the worker sends its marks as ages with `/api/worker/exited`. They are `peak_rss_bytes`, `cpu_seconds` and `peak_cpus` (null where unknown: EC2 and Kubernetes, whose machines' samples stay under Machines; `<binary> run`; on macOS, without `/proc`, peak cores, and any attempt that shared its process with another). The run's page, its attempts' and the pipeline's Resources card (p50 and max of its last 20 measured runs) show them, for #171's requests. *Verified* by `tests/usage.sh`.

**The fleet** (`morca.fleet`, `/fleet`) is every machine at once. The scheduler, every `MORCA_FLEET_SECONDS` (30; 0 turns it off) and only on the ec2 runner or with `MORCA_CONTROL_SAMPLES` set, reads the last 120 lines of each live instance's `metrics/<role>-<instance id>.jsonl` (the file the run's page reads, uploaded every `MORCA_CLUSTER_LOG_SECONDS`) and keeps what it hasn't got in `orca.fleet_samples` (host, time, cores, CPU, busiest core, memory %, fullest disk %, network in and out), trimmed to 30 minutes; each new sample also adds its seconds, CPU seconds used and available, and bytes to `orca.fleet_hourly` (per hour and role), trimmed after 8 days. So a page view reads two small tables and `orca.instances`, never S3, and the run pages' own reads of a whole file are unchanged. The control instance runs a sampler of its own (`morca sample --out <file> --keep 720`, a container the stack's user data starts beside the scheduler with the host's PID and network namespaces), keeping its last hour in a file `MORCA_CONTROL_SAMPLES` names, which the scheduler reads like the others; `MORCA_CONTROL_TYPE` says what the instance is. Without a sampler it has no row. `/fleet` shows summary cards (hosts by role and type, cost per hour at a table of us-east-2 on-demand prices, labelled an estimate, runs running and queued, runs and errors in the last hour with 24-hour sparklines; errors are failed step attempts, including ones a retry fixed, and failed runs, both shown), a sortable table of live hosts that refreshes every 10 s, and for `?range=24h|7d` the hosts over time by role (from the instances' launch and end times), runs started and ended per hour with failures overlaid, and the fleet's vCPUs busy and available and its network throughput (from the hourly rows). The home page has the cards in a compact strip; `/api/fleet` is all of it as JSON. A host that hasn't uploaded yet is `starting`; a worker the scheduler drained is `draining`. *Verified* by `tests/fleet.sh`. Since #220 the page is Ops' Pools (`/ops/pools?kind=ec2`, `morca._internal.ui.pools`): its cards and charts, with EC2 in view, above a row per machine of every pool (EC2 instances live and ended in the last hour, a Kubernetes run's pods, each worker token's machine), filtered by `?pool=` and `?kind=`; a machine's page draws an instance's samples as its run's Machines card does. `/ops/fleet` and `/ops/workers` redirect there, and keep their JSON; the control host is Control's, not a row. *Verified* by `tests/fleet.sh`.

**The watchdog** (`morca.watchdog`) stops the bleeding when the numbers above leave a sane range (on 2026-11-05 nothing noticed ~360 launches in 38 minutes, or a run waiting 3 hours for workers). The scheduler checks six rules every `MORCA_WATCHDOG_SECONDS` (60; 0 turns it off; the first check is on its first tick), each from Postgres only, with the limits of the table in the module's docstring: `launches` (rows of `orca.instances` launched in the last hour that weren't pool handovers, over 200: all pipelines), `cost` (the fleet's price table over the instances up at each minute of the last 15, over $3 an hour sustained, or integrated over the last 24 hours, over $25: all pipelines), `idle` (workers up the whole window and sampled, not draining or pooled idle, 4 or more, averaging under 15% CPU over 10 minutes of `orca.fleet_samples`: the pipelines owning them), `failing` (attempts ended in the last hour per pipeline: over 20 failed, or over half of at least 10: that pipeline), `stuck` (a run with a running attempt and a sampled live host whose newest attempt start or end, instance launch, join or end, and newest sample over 5% CPU are all older than 30 minutes: its pipeline; the window is at most 30 minutes, how long samples are kept, and a run with no samples can't be judged) and `control` (the newest `/system` minute's memory over 90% or fullest disk over 85%: all pipelines). The thresholds are `MORCA_WATCHDOG_LAUNCHES`, `_COST_HOUR`, `_COST_MINUTES`, `_COST_DAY`, `_IDLE_CPU`, `_IDLE_MINUTES`, `_IDLE_WORKERS`, `_FAILED`, `_FAILED_PERCENT`, `_FAILED_MIN`, `_STUCK_MINUTES`, `_STUCK_CPU`, `_MEMORY` and `_DISK`. The rules are pure functions of rows (`eval_*`, tested over made-up rows in `tests/test_watchdog.mojo`); gathering them is the only SQL. A tripped rule pauses the pipelines in its scope that aren't paused already through `morca.pause.set_paused`, which `morca pause` and the Pause button use too, writes an `orca.audit` row per pipeline (user `watchdog`, source `watchdog`, action `/pipelines/<name>/pause`, detail with the rule and its numbers) and a row of `orca.watchdog_trips`. If everything in scope is paused already nothing is recorded, so a rule that stays over its limit doesn't write a row a minute. It never resumes: a trip is *active* while any of its pipelines is still paused, which is when the red banner on `/` and `/fleet` lists it (rule, numbers, when, the pipelines, a link to the evidence), `morca_watchdog_tripped{rule}` is 1 and `/api/watchdog` lists it; unpausing the last one clears all three. A rule still over its limit trips again on the next check, so snooze it first. Each check also stores every rule's value and threshold in `orca.watchdog_rules` (`morca_watchdog_value{rule}` and `_threshold{rule}`, left out when there was nothing to judge), and a snooze (`morca watchdog snooze <rule> 2h`, the form on `/watchdog`, `off` to end one; at most 30 days) is stored there too and audited (`/watchdog/<rule>/snooze`; from the command line without `--remote` as the local user, source `local`). A snoozed rule is still read, but trips nothing. `morca watchdog status [--json]` prints the rules and active trips locally or with `--remote`. A check that fails (the database is down) is printed and tried again. Not covered: the control instance itself dying, which only an AWS Budget alert outside morca can catch; email through SES, left as a follow-up. *Verified* by `tests/test_watchdog.mojo` and `tests/watchdog.sh` (a launch storm against the stand-in EC2, the banner, metrics and commands, snoozes, unpausing, then seeded cost, idle, failing and stuck rows, and the watchdog off).

**The control instance** has its own page, `/system` (`morca.system`). Its sampler (above) also gets `--cgroup` and `--names`: the host's `/sys/fs/cgroup` and `/var/lib/docker/containers`, mounted read-only, from which each Docker container's memory is read by name (`memory.current` less the inactive page cache, as `docker stats` counts it) and put in the line as `containers`. That was chosen over `docker stats`, which needs the Docker socket, a root-equivalent API on the host, in a container that otherwise does nothing but read; the cost is that it depends on cgroup v2's layout (`system.slice/docker-<id>.scope`, or cgroupfs's `docker/<id>`) and on Docker's `config.v2.json` for names (without it a container is its short id). The scheduler reads the control file in the same pass as the fleet's and rolls the lines it hasn't got into `orca.system_minutes` (a row a minute: sums to average over, peaks, the fullest disk's bytes) and `orca.system_containers` (a container's peak a minute), kept 14 days; "hasn't got" is the newest `last_t`, so a pass again adds nothing. It also appends the raw lines to `<MORCA_LOGS>/control/<UTC date>.jsonl`, uploaded whole every `MORCA_CONTROL_UPLOAD_SECONDS` (300) and once a day is over; the stack's bucket expires `logs/control/` after 14 days, and a local `MORCA_LOGS` has older files removed. The page, like `/fleet`, reads Postgres only: cards (CPU, memory, the fullest disk with its path, network), a table of containers with their memory now and peak, and for `?range=24h|7d|14d` (points every 5, 30 and 60 minutes; a point with no samples is 0) charts of CPU, memory, disk, network and each container's memory; `/api/system` is the same as JSON. **`/metrics`** is Prometheus' text format, gauges only: `morca_control_{cpu_percent,memory_used_bytes,memory_total_bytes,memory_percent,disk_used_bytes,disk_total_bytes,disk_percent,network_in_bytes_per_second,network_out_bytes_per_second,sample_age_seconds}`, `morca_control_container_memory_bytes{container}`, `morca_runs{status="running|queued"}`, `morca_fleet_hosts{role}`, `morca_runs_started_last_hour` and `morca_errors_last_hour{kind="step_attempts|runs"}`; the control instance's are left out once its newest sample is ten minutes old. Like every read it needs no login. The home page, and `/system`, **warn** when the fullest disk is over 85% or memory over 90% (the newest minute's), since a full disk stops Postgres and so every run; `/`'s JSON has them as `warnings`. *Verified* by `tests/system.sh` (sample files in, rows and day files out, a pass again, expiry, the pages, the gauges, a full disk and the thresholds, stale and missing samples) and, for the container reads, `tests/sample.sh` over a made-up cgroup tree. Not verified: a real instance's cgroup layout (see the PR for how to check it).

- **The taxi gate** runs by hand: it downloads 1.2 GB. CI runs the pipeline on two real months sliced to about 500 rows each (`tests/fixtures/taxi`, written by `tests/taxi_fixtures.mojo`): a run, and a run whose download fails, resumed.

## Phase 2: schedules and partitions

Gate: a schedule fills each month's partition as it falls due, and a backfill over 2011–2024 runs with a bounded number at once.

- **Partition definitions** on the pipeline: `partitions=Monthly["2011-01"]` or `Daily["2024-01-01"]`, so the scheduler knows the set of keys and which are due.
- **Cron**: five-field expressions with ranges, steps and lists, and a time zone. Time zones are read from the system's TZif files (`/usr/share/zoneinfo`), which is a small, documented format. A schedule says which partition a fire fills, e.g. "at 03:00 on the 2nd, the previous month".
- **The `morca` scheduler binary**: registers pipelines from their `describe`, ticks once a second, creates runs that are due, starts them as subprocesses, retries failed runs with exponential backoff and jitter, and enforces `max_runs` per pipeline by counting `running` rows in the same transaction that starts one.
- **Backfills**: one run per partition over a range, queued, started `max_runs` at a time. This is also how partitions run in parallel, in place of phase 1's `max_parallel`.
- **Missed fires** after the scheduler was down are caught up once each, not dropped and not fired many times; a pipeline can say `catchup=False`.

### How it fits together

- **A partition key is a type.** `Month` and a new `Day` share a `Key` trait (parse, write, next, compare). `Monthly[start]` and `Daily[start]` are partition sets over them, with the range syntax the command line already takes (`2024-01..2024-03`, comma lists). `Pipeline` takes `partitions=`, and its first step must take that key (a `Mapped` step) or a `Seq` of it (a `Gather` step), checked at compile time like any other edge. A pipeline that leaves it out is `Monthly` with no start, as in phase 1, and can't be scheduled or backfilled from the beginning.
- **A schedule is declared with the pipeline**: `schedule=Cron["0 3 2 * *", "America/New_York"]` and `fills=Previous` (the key before the one the fire falls in) or `Current`. `describe` prints the partitions and the schedule, so the scheduler learns both without linking the pipeline.
- **Registration.** `morca register ./build/taxi` runs `taxi describe` and stores the binary's path with the DAG in `pipelines` (`binary_path`, and `since`, when its schedule starts counting). The scheduler reads the pipelines it schedules from Postgres, and their schedules, partitions and limits from the stored JSON in SQL; there is no configuration file and no JSON parser. Registering a new build moves the pipeline's queued runs to its registry hash, and its failed runs waiting for a retry that have no step done. A retry of a run with steps done by other code would be refused by the binary's `resume`, so the scheduler fails it instead of starting it, with an error on the run (`runs.error`, shown by `<binary> status <run>` and the run's page) saying to resume it with the new code; a local run whose process exits before claiming it fails with the exit code and the last line it printed as its error. Only `morca register` moves a pipeline's code: `<binary> run` records a pipeline that isn't registered yet, but leaves a registered one's hash and `describe` alone, and refuses (exit code 2) a binary whose code isn't the registered one's unless it's given `--allow-new-code`; such a run counts as its own code's, so it makes nothing done for the pipeline. *Verified* by `tests/new_code.sh` and `tests/manual_run.sh`.
- **A fire is a row.** `fires` (pipeline, fire time, partition, run) has a unique (pipeline, fire time), and the scheduler inserts the fire and its `queued` run in one transaction, so a scheduler killed and restarted mid-tick doesn't fire twice. Backfills insert queued runs the same way, with trigger `backfill`.
- **One live run per partition.** Every path that queues a run (a fire, a sensor, a rebuild's level, the UI's start, a backfill) checks for a live run of the same keys, in the transaction that would queue it and under a lock on the pipeline's row, so two runs never run one partition at once and both append. A fire records the live run as its run, a sensor leaves the keys to it (and records it as the snapshot's run if no other key is left), a rebuild's level waits until it has ended, the UI refuses with the run's ID, and a backfill skips the key. A partition that's done is not protected: a later fire, sensor, rebuild or start runs it again, and its steps append again unless they replace it (`replaces=`, "Replacing partitions"), so `morca register` warns of a schedule that fires more than once for one partition (`0 */6 * * *` on `Daily`). *Verified* by `tests/one_run_per_key.sh` and, for sensors and rebuilds, `tests/sensors.sh`.
- **Starting a run is `resume`.** A queued run has nothing done and no heartbeat, which is exactly what `taxi resume <run>` already takes. The scheduler forks and executes the binary (`fork` and `execv` through FFI, as dista starts its local processes) and doesn't wait on it beyond reaping it: the run records its own progress, and a run whose process dies is found by its stale heartbeat.
- **`max_runs`**: the scheduler starts a queued run only if, in the same transaction and under a lock on the pipeline's row, fewer than `max_runs` of the pipeline's runs are live. It marks a run `running` with itself as owner and no heartbeat when it starts it, and the process's claim takes it from there. A run is live while its heartbeat is fresh, or, before the claim, for the stale limit after the scheduler started it; after that its process is taken to have died.
- **Retrying a failed run** is resuming it again, up to `run_retries` times (3 by default), after `MORCA_RETRY_SECONDS` (60) doubling with each start, plus up to a tenth more as jitter. A run whose process died is started again at once, within the same budget. Only scheduled, backfilled and sensed runs are retried. A pipeline's own `retry_seconds` replaces `MORCA_RETRY_SECONDS`, and `max_retry_seconds` caps the doubling, so `run_retries=72, retry_seconds=3600, max_retry_seconds=3600` tries hourly for three days. A step's retries inside a run wait its `backoff_seconds`, doubling. A manual, UI or rerun run whose process died is marked `failed` (`interrupted: its process stopped`) by the next tick, so it can be resumed or cancelled; a run whose process died never holds its keys from a backfill or a keyed sensor, which queue them again. `morca backfill` prints on stderr the keys it left and why: done, or in live run N. *Verified* by `tests/dead_runs.sh`.
- **Missed fires**: on each tick the scheduler computes the fires between a schedule's last recorded fire and now. With `catchup=True` (the default) each becomes a queued run, at most `max_runs` running at once; with `catchup=False` only the latest does.
- **Time in tests.** `MORCA_NOW` (`2024-03-10T07:00Z`, or epoch seconds) fixes the clock of `fires` and the scheduler, and `morca tick` runs one tick and exits, so the tests step time forward deterministically.
- **Daylight saving.** A cron time that a spring-forward skips fires at the first minute after the gap; one that a fall-back repeats fires once, at its first occurrence. That's what Vixie cron and systemd timers do.
- **The time zone rules** come from TZif version 2 and later: the 64-bit transition times, then the footer's POSIX `TZ` string (such as `EST5EDT,M3.2.0,M11.1.0`) for times after the last transition, which "slim" TZif files rely on for every year since 2007.

### How the gate went

Done by hand on one Mac (10 cores, 24 GB) from the 168 TLC files, 19 GB, already downloaded: `morca register ./build/taxi`, `morca backfill taxi 2011-01..2024-12`, then `morca scheduler` with `MORCA_NOW` fixed at 2025-01-15. All 168 runs succeeded on their first start, never more than 4 running, in 11 minutes, with 336 commits (a load and a compaction per month). The table holds 1,438,321,685 rows for 2011–2024, one file per month; its 2023–2024 months are still phase 1's 79,478,796. A tick at 05:59 on 2 February 2025 fired nothing; at 06:00 it fired once, for 2025-01, and that run downloaded the month from the TLC and loaded its 3,475,204 rows.

What it took:

- **The 2011–2022 schemas.** Every file from 2011 has the same 19 columns; only the types move. Before 2019 `congestion_surcharge` and before 2021 `airport_fee` are null, and a file whose column is all null types it as int32, not double. iceberg's writer already casts to the table's type, and an all-null int32 column stays null, so the load needed no change.
- **Each run compacts only its months.** Phase 1's compaction rewrote every month with more than one file; with four runs loading at once it would rewrite the others' half-loaded months. It now rewrites the months its own loads loaded.
- **Seeding `std.random` in each process.** The first attempt at the gate failed compactions with "none of the files this commit removes is in the current snapshot". iceberg draws snapshot IDs and file UUIDs from `std.random` and never seeds it, so every pipeline process drew the same sequence: concurrent runs committed snapshots with the same IDs and wrote each other's `snap-<id>` manifest lists. `morca_main` now seeds it from the clock and the process ID, and `tests/taxi.sh` commits from two runs at once and checks the snapshot IDs and manifest lists are distinct; without the seed it fails. iceberg should seed it itself.
- **Memory.** A 2011 month is 14 to 16 million rows in one row group. Loading one peaks at about 4 GB and compacting it at about 6 GB, mostly iceberg's writer copying the batch to align it and again per partition; four at once peaked at 15 GB. Streaming the compaction's reads didn't change that, so it's left to iceberg's writer.
- **The schedule** fires at 06:00 UTC on the 2nd for the month before. The TLC publishes a month about two months after it ends, so in real time that fire fails its download and is retried with backoff until its budget is spent; a backfill of the month once it's out loads it. A fill with a lag is left for later.

## Phase 3: the UI

Gate: a failed step is found, its logs read and the run resumed, without a terminal.

**Decided: server-rendered HTML from flare, with a little JavaScript for the live parts.** It keeps the footprint at one process with nothing to build: no Node toolchain, no bundler, no client-side state. Every page is also the API: the same path answers JSON to `Accept: application/json` (or `?format=json`), so the command line, scripts and the UI read one thing and can't drift. A single-page app can be evaluated later, if a view needs more than this gives it (a zoomable DAG, a live Gantt chart); the JSON paths are what it would be built on.

### How it fits together

- **`morca ui`** is a command of the `morca` binary, not a new binary: it needs `MORCA_DATABASE_URL` like the others, reads the tables the scheduler and the runs write, and binds `127.0.0.1:8270` unless `MORCA_UI_ADDR` says otherwise. `MORCA_UI_LINKS` adds a deployment's own links to the nav after Docs, as comma-separated `label=url` entries (`Census ↗=https://census.mlake.dev`); labels and urls are escaped and only http(s) urls are kept. `MORCA_POSTHOG_KEY`, a PostHog project key (`phc_...`, public), adds the magmalake.org website's PostHog snippet to every page's head, with `site: "morca"` registered on each event; it loads `/ph/static/array.js` and sends to `/ph` on the UI's own origin, which a first-party proxy in front of the UI has to serve (orca.mojourney.dev: the `mojourney-ph` Worker in magmalake/magmalake.org), and keeps nothing in cookies or `localStorage`. Unset, or anything not a `phc_` key, adds nothing. It holds no state of its own, so it can run beside the scheduler, or several of it at once.
- **flare serves it**: one handler (`morca._internal.web.server`) that looks each request up in a route table (`morca._internal.web.routes`; see [Web layer](#web-layer)), one reactor thread (`num_workers=1`) to start with. A request runs a few short queries against indexed columns, so it doesn't hold the loop for long; idle and write timeouts are set for the work rather than left at flare's web defaults (see flare's silent-reap history). Postgres is reached through one connection per request at first, measured, and pooled only if that shows.
- **HTML is written in Mojo**, through a small `morca.html` writer that escapes every value it's given and only writes raw markup it's told is markup. flare's template engine was looked at and isn't used: its context is strings and lists of strings, and a run page is a table of records.
- **The page skeleton**: one layout with a header (pipelines, runs) and one stylesheet with magmalake.dev's colours and type, light and dark. Nothing is fetched from elsewhere, so the UI works without the internet.
- **Live parts are polled fragments**: a running run's DAG and steps, and a running attempt's log, sit in an element with `data-poll` naming a fragment path that returns only that piece of HTML. Twelve lines of script in the layout replace it every two seconds until the fragment answers 286 (htmx's "stop polling"), which it does once what it shows has ended. htmx was the plan; for this one pattern it would have been 50 KB to embed in the binary. Forms are plain HTML forms, so the actions need no script either. Server-sent events are left for later; flare has them, but polling a few fragments is simpler and plenty for one team.
- **The DAG is drawn server-side as SVG**: steps laid out left to right by their order, mapped steps drawn as a stack, edges from `after`, each box coloured by the status of its partitions in the run being shown. A pipeline is a chain today, so the layout is a row; it's written for a DAG, as phase 4's datasets may branch.
- **The Dista timeline** is served from the run's log directory as `timeline.json`, linked for opening in Perfetto, rather than drawn by morca. The directory is found from the run's attempts' log paths, so the UI needn't share the runs' `MORCA_LOGS`; a relative `MORCA_LOGS` is relative to where the run was started, which the UI must share.
- **Actions go through Postgres, never through the UI's process.** The UI doesn't start pipeline binaries: it writes a row and the scheduler, which already starts and limits runs, acts on it. So `max_runs`, retries and ownership stay in one place, and the UI works the same whether the scheduler is on this machine or not.
  - **Start a run**: a queued run over the partitions entered, trigger `ui`.
  - **Resume** a failed, cancelled or stalled run (`running`, with a heartbeat older than the stale limit): it's queued again (`retry_at` cleared), and the scheduler resumes it as it does a retry. A resume of a run whose code has changed asks for confirmation, which sets `allow_new_code` on the run, and the scheduler passes `--allow-new-code`.
  - **Rerun from a step**: a new run, trigger `rerun`, over the same partitions, with the steps before the chosen one that succeeded copied from the old run (their inputs and outputs, and `copied_from` naming the step each came from, whose attempts, reads and commits stay with it), so `resume` runs the chosen step and what follows. The old run is left as it was. A run whose pipeline's code has changed since can only be rerun from the first step, as the old code's outputs may not be what the new code reads.
  - **Backfill a range**: what `morca backfill` does; with its checkbox checked, what `morca backfill --rerun` does.
  - **Cancel**: a queued or failed run is `cancelled` at once (a failed one is then not retried). A running one gets `cancel_requested`: the run checks it where it already checks its ownership, before each attempt, and ends `cancelled`; if its process has died, the scheduler ends it `cancelled` instead of starting it again. A step already running gets `MORCA_CANCEL_KILL_SECONDS` (default 60, read by whatever cancels it and kept as `runs.cancel_at`) to finish its attempt; past that the run's own watchdog, its heartbeat thread, fails the attempt, ends the run `cancelled`, writes an `orca.audit` row (user `morca`, action `stop`) and exits the process, which takes a local run's dista processes with it. The scheduler's sweep then removes the run's pods or instances, as for any run that isn't running. A commit the stopped step made is recognised when it's run again (see "Snapshots"). *Verified* by `tests/stop.sh`.
  - **Cancel in bulk**: what `morca cancel <pipeline> KEYS|@all` does, from the pipeline page (`partitions`, empty for all): each of the pipeline's runs over any of the keys (a run of several keys whole) that is queued, running, or failed and due a retry is cancelled as above. A failed run with no retries left, and one that ended, are left as they are. Added after a 31-run backfill had to be cancelled in SQL.
  - **Pause**: `morca pause <pipeline>` (or the page's button) sets `pipelines.paused` (migration 16), and the scheduler starts none of the pipeline's runs: fires, sensors, retries and backfills still queue theirs, which wait, and runs already going go on. `morca unpause` lets the scheduler start them on its next tick. A paused pipeline says so on `/` and its page, and in their JSON (`paused`).
- **An action answers `303 See Other`** to the page of the run it made or acted on (or, to `Accept: application/json`, that run's ID). One that can't be done (a run still going, a range with a bad key) answers 409 with the reason, on a page with a way back; a resume onto new code answers 409 with the form that confirms it.
- **No authentication in phase 3** (one team, a trusted network). Because the UI is on localhost and its actions change state, every `POST` checks that `Origin` (or, without it, `Referer`) is the UI's own, so a page on another site can't make the browser post to it. The UI's own origin is `Host` with the scheme the browser used: `X-Forwarded-Proto` behind a proxy that terminates TLS (`MORCA_UI_TRUST_PROXY=1`, as `morca aws up` deploys Caddy), else `https` with `MORCA_UI_SECURE_COOKIES=1`, else `http`; scheme and host compare in any case, and a default port is left out. Nothing changes state on a `GET`.

A request's way through: `web/server` finds its route, checks the origin
and who it's from, and calls the route's handler with a `Call`. For the
run page and the pipeline page the handler reads the view once
(`run_view`, `pipeline_view`), and the page is that view twice: its JSON
(`api/runs.run_json`, `api/pipelines.pipeline_json`) and its HTML
(`ui/run.run_html`, `ui/pipeline.pipeline_html`). The other pages still
build both in one function in `ui/`, over the rows of `views/`; they can
be split the same way as they change.

The worker API is apart from the rest: a worker's token gets nothing
elsewhere and a user's nothing there, and `MORCA_WORKER_ADDR` serves it on
an address of its own, from a thread of its own, so a slow page can't hold
up claims, heartbeats and store calls (docs/workers.md).

## Phase 4: lineage and sensors

Gate: committing a new snapshot to a source table rebuilds exactly the tables downstream of it.

Phases 1 to 3 already record every table read and commit: `reads` and `commits` in Postgres, and `morca.*` properties in each committed snapshot's summary. What's missing is a name for a table that means the same thing in every pipeline, the graph across pipelines that those names make, queries over it, and runs started by it. A pipeline in phase 4 still runs by itself; what changes is that morca knows which pipelines feed which.

### How it fits together

- **A dataset is a name, `namespace.table`**, such as `nyc.trips`. Today a table is known by its location, which depends on where the warehouse is (a local path, later `s3://`). A name doesn't, so two pipelines that name `nyc.trips` mean the same table in every deployment. `MORCA_WAREHOUSE` is the root of a filesystem catalog (iceberg's `catalog.filesystem`): `nyc.trips` is `<warehouse>/nyc/trips`. Phase 5 points it at S3; a REST catalog can come later behind the same names.
- **A step declares what it reads and writes**: `Step[..., reads=["raw.trips"], writes=["nyc.trips"]]`. `ctx.table("nyc.trips")` loads a declared dataset from the warehouse. `scan` raises for a dataset the step didn't declare in `reads`, and `append` and `commit` for one it didn't declare in `writes`, naming the step and the dataset. So the graph is known before anything runs, and it can't drift from what the steps do. A step may read and write one dataset (the taxi compaction does). A table that isn't in the warehouse, such as a test's temporary table, can still be scanned and appended to by location, as now, and isn't part of the graph.
- **`describe` lists each step's `reads` and `writes`**, so `morca register` knows every pipeline's datasets without linking it. Registration refuses a pipeline that would close a cycle across pipelines: A writes X, B reads X and writes Y, and A reads Y. A pipeline that reads and writes one dataset is not a cycle.
- **`reads` and `commits` gain a `dataset` column** (a migration), null for a table outside the warehouse. Lineage queries join on it; the location stays, as it says where the snapshot is.
- **Lineage is two walks** over `commits` and `reads`, in SQL (recursive CTEs):
  - **Back** from a snapshot: the attempt that committed it, its step, run, partition and code, the snapshots that attempt read, and, for each of those, the attempt that committed it, back to snapshots no morca run made (a source).
  - **Forward** from a snapshot: every attempt that read it, what each committed, and so on.
  
  Both are bounded by a depth (default 20) and return edges, so a deep graph is cut, not slow. They're checked against the snapshots' own `orca.reads` summaries, which carry the same edges in the tables themselves.
- **Partitions across pipelines.** A sensor or a rebuild has to say which partitions of the downstream pipeline to run. A snapshot a morca run committed says which partitions it holds: a mapped step's commit has `orca.partition`, and a gather step's commit gains `orca.partitions`, the run's keys. A snapshot committed by something else carries no keys; its writer can set `orca.partitions` in its summary, and without it the downstream pipeline runs the partition its schedule would fill now (its `fills` partition), or, unscheduled, its latest partition by the clock. Keys move between partition kinds as they contain each other: a day upstream is the month that contains it downstream, and a month upstream is each of its days downstream.
- **Sensors are opt-in per pipeline**: `Pipeline[..., sensor=True]` runs it when a dataset it reads gets a new snapshot. There are two ways the scheduler learns of one:
  - **From Postgres, for snapshots morca made.** A succeeded run's commits are in `commits`, so the scheduler sees them on its next tick, without reading any table.
  - **By polling, for snapshots something else made.** The scheduler links no iceberg, so it runs `<binary> sense`, a new command of every pipeline binary, every `MORCA_SENSE_SECONDS` (default 60). It prints the current snapshot ID of each dataset the pipeline reads: one metadata read per dataset.
  
  `orca.sensed` records, per pipeline and dataset, the last snapshot that started a run, so each new snapshot starts one run once, as a fire does. The run's trigger is `sensor`, and it records the snapshot that started it. A run is started only for a snapshot committed after the pipeline was registered, so registering doesn't rebuild history; a backfill does that.
- **"Rebuild downstream of this table"** queues runs for every pipeline reachable from a dataset in the graph, over the partitions given, in dependency order. Each pipeline is placed at its longest distance from the dataset, so one that reads two rebuilt datasets runs after both. A rebuild is a row (`orca.rebuilds`), and its runs carry its ID. The scheduler queues the pipelines at the next distance once every run at the ones before has succeeded, and stops if one fails, so it can be resumed from the UI as a run is. It's in the UI on a dataset's page and on the command line as `morca rebuild <dataset> KEYS`.
- **In the UI:**
  - **`/datasets`** lists every dataset with its writers, readers and latest snapshot.
  - **`/datasets/<name>`** shows the graph of pipelines and datasets around it (drawn server-side as SVG, like the DAG), its snapshots, newest first, with the run that made each, and the rebuild form.
  - **`/datasets/<name>/snapshots/<id>`** shows the lineage back and forward, as a graph and as a table.
  
  A run's page links the datasets it read and committed.

These tests need iceberg, so they run in the `data` environment, as the table tests do.

As built (`morca.sensors`, `morca.warehouse`):

- **`sense` reads metadata JSON itself.** A pipeline imports iceberg only if it uses tables, but every binary answers `sense`, so `morca.warehouse` finds the current metadata file as iceberg's filesystem catalog does and reads just the current snapshot's ID and its summary's `orca.run` and `orca.partitions`. It prints `<dataset> <snapshot> <orca|other> <partitions|->`; the scheduler polls it only for snapshots something other than morca made. A dataset the pipeline also writes isn't sensed, so the taxi compaction doesn't start its own pipeline.
- **"Registered" is when it became a sensor.** `morca register` asks a sensor's binary to `sense` and records what its datasets hold then as seen, with no run, and `pipelines.sensing_since` dates the commits it counts from. Registering it again keeps both; one registered as no longer a sensor loses `sensing_since`, so if it becomes one again it starts afresh. A sensor that reads no dataset is refused.
- **One run per tick per sensor.** `orca.sensed` has a row per pipeline and snapshot, inserted in the transaction that queues the run, so the snapshots one tick sees start one run over all their partitions, and none starts a second. A sensor's run is retried like a scheduled one.
- **A snapshot a sensor can't run is seen all the same.** One whose keys aren't partitions of the sensor's kind (a week another writer put in `orca.partitions`, or names reaching a dated sensor) gets its `orca.sensed` row with no run and the reason in `error`, and is said once; the other snapshots the tick saw start their run. Otherwise one such snapshot would roll back the tick's transaction on every tick, and no later snapshot of any of the sensor's datasets would run. A pass that fails (a `sense` or `keys` that exits non-zero) is kept as the pipeline's `sense_error` and printed when it changes, not every second; a pass that works clears it. The pipeline's page in `morca ui` shows both.
- **A slow binary holds up nothing else.** The scheduler asks a sensor's `sense`, and a keyed sensor's `keys`, in a child process it checks on from tick to tick rather than waits for, its output in a file of its own, so one hung S3 endpoint or a keys column of millions of rows doesn't stop fires, retries, dead-run detection or sweeps for every pipeline. A child still going after `MORCA_BINARY_SECONDS` (default 300) is killed, with what it started (it leads a process group), and the pass fails saying so, which is the sensor's `sense_error`. `morca tick`, having no next tick, waits for them. `describe` at registration, `keys` for a backfill and every other `capture` take the same limit; `dista-status` and `dista-drain`, asking an EC2 run's head each tick, take 10 s, after which that run isn't scaled this tick. A keyed sensor reads its keys again only when its keys dataset has a snapshot newer than the one they came from, and keeps them in `orca.keys`, which the UI's keyed page shows while they're younger than `MORCA_SENSE_SECONDS`; older, the page runs `keys` itself for at most 10 s, showing the kept ones with a note if that runs out. *Verified* by `tests/binary_timeouts.sh`.
- **A rebuild's plan is a table**, `orca.rebuild_pipelines`: each pipeline downstream, its level, its partitions (the keys given, moved to its kind) and its run. Commits made by a rebuild's runs don't start a sensor in a pipeline the rebuild runs itself, so `report` runs once, after `clean`, not also as a sensor. The scheduler doesn't retry a rebuild's runs: one that fails stops the rebuild (`failed`), and resuming it from the UI carries it on. `/rebuilds/<id>` shows the plan and its runs.

## Keyed partitions

Gate: a pipeline partitioned by the 20,000 log IDs of a dataset backfills every log in runs of 100 at most `max_runs` at once, and when rows are added to that dataset, runs start for the new logs only.

Months and days are the only partition keys so far, and the `Key` trait assumes a calendar: `next`, `prev` and `containing(year, month, day)` exist so ranges, `fills` and sensors can move between keys by date. A lot of data isn't partitioned by date. The first consumer is labelrefinery's auto-labeling of the Argoverse 2 LiDAR dataset, which is 20,000 recordings named by UUID: a mapped step per recording, a gather step scoring all of them. Its keys are names, there are too many to write in the source, and more arrive later. This section adds a third kind of partition for that, independent of phase 5 and buildable before it.

### How it fits together

- **The `Key` trait splits in two.** `Key` keeps what every key has: `parse`, `write_to`, equality and an order (`__lt__`, used for sorting and display only). `TimeKey(Key)` adds `next`, `prev` and `containing`; `Month` and `Day` implement it. Everything that does date arithmetic (ranges, `fills_for`, the scheduler's fires, the sensors' day↔month mapping) asks for `TimeKey`, so using it on a key that isn't a date is a compile error rather than a runtime surprise.
- **`Name` is the new key**: a string of 1 to 128 bytes from `[A-Za-z0-9._:/-]`, without two dots in a row, and with a `/` only between other bytes, one at a time (so `owner/name` is a name, and `/a`, `a/` and `a//b` aren't). Since neither a comma nor `..` can appear in one, the command line and the stored `runs.partitions` text stay unambiguous. It orders by bytes. Where a name becomes one segment of a path, an attempt's log directory, it's written with `/` as `%2F` (`morca.name.path_segment`), and the UI's links encode it the same way, so `owner/name`'s page is `/pipelines/<p>/keys/owner%2Fname`. `/` was added after gharchive.example needed repositories as keys.
- **`Keyed[dataset, column]` is the partition set**: `partitions=Keyed["av2.logs", "log_id"]`. Its keys are the distinct values of `column` in the current snapshot of the warehouse dataset `dataset`. Keys live in data rather than in the source because there are thousands of them and they grow, and because "which logs exist" then has snapshots and lineage like anything else. The first step takes a `Name`, or a `Seq[Name]` for a first gather step, checked at compile time as for `Monthly`. `describe` writes `{"kind": "keyed", "dataset": ..., "column": ...}`.
- **Keyed pipelines are refused things that need a calendar**, at compile time: `schedule=` and `fills=`. A keyed pipeline runs by `run`, by `backfill`, or as a sensor of its keys dataset (below). A cron schedule over names has no partition to fill, and guessing at one (all keys? new keys?) is a sensor's job done worse.
- **`<binary> keys`** prints the keys dataset's current snapshot ID and then its keys, one per line, sorted. A value of the column that isn't a name, or is null, isn't a key: it's left out, and `keys` says on stderr how many there were, with the first few, so one odd row doesn't make every key unreadable. Like `sense`, it exists so the scheduler, which links no iceberg, can learn a pipeline's keys. It reads the one column through `morca.tables`, so only binaries with a keyed pipeline import iceberg for it.
- **On the command line**, `--partitions` for a keyed pipeline takes a comma-separated list of names, or `@all` for every current key, or `@file:<path>` for a list one per line, which scripts and the labelrefinery side need for samples. A range (`A..B`) is refused with a message saying keyed partitions take lists. A key that isn't in the current keys snapshot is refused, so a typo doesn't make a run of nothing.
- **Many keys per run.** A run over a list of keys is already what phase 1 does: a mapped step runs once per key, one after another in the driver, each free to use dista inside, and a gather step runs once over all of them. Keyed pipelines are where that matters, since one run per key would mean 20,000 driver processes and as many dista runtimes. So the pipeline gets `keys_per_run: Int = 1`, and for a keyed pipeline the default to recommend is in the tens to hundreds. Parallelism is then `max_runs` runs at once, each using dista inside its steps. Time-partitioned pipelines keep one key per run by default; the parameter works for them too.
- **A key is done** when every mapped step of the pipeline has succeeded for it in some run whose registry hash is the pipeline's current one. That's a query over `steps` and `runs`, not a new table. A key whose run failed partway still has its succeeded steps; resuming the run reruns only what didn't succeed, as now.
- **Backfill picks undone keys and batches them.** `morca backfill <pipeline> @all` (or a list) takes the keys given, drops those that are done or in a live run (queued, or running with its process alive), sorts the rest and queues one run per `keys_per_run` of them, all with trigger `backfill`. This replaces today's duplicate check, which compares a run's whole `partitions` text and so can't see a key inside a batch. Time-partitioned backfills use the same per-key check, so their behaviour doesn't change. `morca backfill --rerun` (the backfill form's checkbox, `rerun=1`) queues the done keys too, for a key whose source has changed since it ran, such as a day that ran out of an API's budget; a key in a queued or running run is still left to that run. For a pipeline whose steps append, a rerun of done keys is refused without `--allow-append` ("A rerun that would append again is refused").
- **Gather steps cover their run's keys.** With batches, a gather step sees its batch, not the whole dataset. A score over all 20,000 keys is a second pipeline, a sensor on the dataset the first one writes, with one gather step and no partitions of its own. That keeps runs bounded and the scoring rerunnable alone. A pipeline that wants one gather over everything can still run `--partitions @all` as one run.
- **Sensors on the keys dataset start runs for new keys.** A keyed pipeline with `sensor=True` is also sensed on its keys dataset, whether or not a step reads it. When that dataset gets a snapshot, the scheduler runs `<binary> keys`, takes the keys that aren't done and aren't in a live run, and queues them in batches of `keys_per_run`. `orca.sensed` records the snapshot as for any sensed dataset, so each snapshot starts its batches once. Keys removed from the dataset aren't unlabeled or deleted; they just stop being offered to backfills.
- **Sensors on other datasets map keys by equality.** A snapshot committed by a mapped step of a keyed pipeline carries `orca.partition` (one name), and one by a gather step carries `orca.partitions` (its run's names). A keyed sensor downstream runs those keys if they're in its own keys dataset, and ignores the rest. Mapping between a keyed and a time-partitioned pipeline is refused at registration, since no rule turns a name into a month. The keys dataset itself needs no mapping, so a time-partitioned pipeline may write it: a daily pipeline that finds new repositories can write the keys a keyed sensor runs, and each of its snapshots offers the keys it holds.
- **In the UI** a keyed pipeline's page shows its keys dataset, how many keys it has, how many are done, how many are in live runs and how many failed, with the failed ones listed and a link to rerun them. The partitions field of the backfill form accepts the same lists as the command line, and `@all`, but not `@file:<path>`: the UI would read the file on its own host, so it answers 400 instead. On the command line, a line of the file that isn't a name is named by its number, not its text. `/pipelines/<name>/keys/<key>` shows one key's steps across the runs it was in.

### Not decided here

- **Running several keys of a mapped step at once inside one run.** One driver runs a batch's keys one after another, as phase 1 does, and any parallelism within a key goes through dista. Dispatching a whole batch's keys as dista tasks would make one run use a cluster better, but a step is a function in the driver, not a dista task, so it's a change to the programming model. It's worth measuring on labelrefinery's first backfill before deciding.
- **Keys from somewhere other than a warehouse dataset**, such as a listing of an S3 prefix. A small pipeline that writes the listing to a dataset does this today, with lineage, so nothing is built for it until that's shown to be too slow.

## Phase 5: on Kubernetes

Gate: the taxi pipeline runs on a schedule on EC2, each run on its own cluster of instances.

- **The scheduler as a Deployment** with one replica and Postgres beside it (or RDS).
- **A run as a dista cluster**: the scheduler creates a head, a worker set sized by the pipeline, and a Job for the driver, all labelled with the run ID, through the Kubernetes API over HTTPS with the pod's service-account token; and deletes them when the run ends. The run's pipeline image is named in its registration.
- **Logs and timelines in S3**, through `MORCA_LOGS=s3://...`.
- **Cluster start time** is measured here. If it dominates short runs, a warm pool of workers per pipeline image is the next step, not before.

[K8S.md](K8S.md) says who creates the pods, how morca talks to Kubernetes, what it needs on AWS and how cost stays bounded. Phase 5 is built and tested on a kind cluster on one machine first, as dista's Kubernetes support was (`deploy/`, `tests/kind.sh` in dista), so only the last PR needs AWS.

**Login for the UI's actions** (`morca.auth`), added before the UI is on AWS: reading needs no login, and every action does once login is on, which `MORCA_UI_LOGIN=required` (set in `deploy/k8s`) or any user turns on. Users are added with `morca user add`; their passwords are bcrypt hashes made by pgcrypto (migration 9), sessions are 32 random bytes kept as their SHA-256 digest and sent as an `HttpOnly`, `SameSite=Strict` cookie (and `Secure` with `MORCA_UI_SECURE_COOKIES=1`), and every action is a row of `orca.audit`, shown on its run's page. Behind an ALB that asks for a login itself, trusting its signed identity header instead is a later step: it needs the header's ES256 signature checked, which nothing in magmalake does yet.

**The `morca` command against the deployed UI** (`morca.remote`, `morca.tokens`; issue #111), added once operating the census meant `aws ssm start-session` and `sudo docker exec scheduler morca ...`. `morca login https://<host>` asks for a user's name and password (no echo; a piped line with `--user`), posts them as JSON to `/api/login`, and stores the API token it answers in `~/.config/morca/credentials` (`MORCA_CREDENTIALS`), keyed by URL. Then `morca --remote <host> <command>` (or `MORCA_REMOTE`) sends `backfill` (with `--preview`), `start`, `cancel`, `pause`, `unpause`, `resume`, `rerun` and `rebuild` to the UI as JSON `POST`s to the paths its buttons post to, and reads `status` and `lineage` from its pages' JSON; without a remote, every command works over `MORCA_DATABASE_URL` as before. The choices, each for a reason:

- **Tokens, not the session cookie, and not the password each time.** A token is `orca_` and 32 random bytes in hex (256 bits, as a session's), shown once, in the login's answer, and kept in `orca.api_tokens` (migration 22) only as its SHA-256, with its user, a label (the machine's host name), when it was made and last used, and when it expires: `MORCA_API_TOKEN_DAYS` (default 30) days on, or fewer with `morca login --days N`. A fast digest is enough for a random 256-bit secret; a slow one (bcrypt) protects guessable ones. A request sends it as `Authorization: Bearer`; one that's unknown, malformed, expired or revoked gets 401, and the cookie is never looked at in its place. `morca logout` revokes it (`/api/logout`), `morca user tokens <name>` and `morca user revoke <name> <id>|@all` let whoever has the database see and revoke a user's, and a new password or a removed user revokes all of hers, as it ends her sessions.
- **The same code as the buttons.** The UI turns the JSON object into the form its own pages post (`_json_form`), so `_act` does the action with the same checks and refusals, and the same `orca.audit` row, with a new `source` column: `ui` for a session, `cli` for a token, which the run's page shows. A refusal is the button's 409 with its reason, which the command prints as its local twin would (`morca: pipeline toy is paused already`), and output matches the local command's (`queued 31 runs`, with the backfill's skipped keys on stderr, which its JSON now carries). `morca status [<pipeline>]`, `morca start`, `morca resume`, `morca rerun`, `morca cancel <run>` and `morca backfill --preview` are new locally too, done through the same pages and actions in the process, so local and remote print the same lines. Reads send no token: the pages are public, and the token travels only with what needs it.
- **CSRF.** A browser's `POST` still needs the UI's own `Origin` (or `Referer`) and a session, as before. A request with an `Authorization` header, or a JSON login for a token, skips that check only when it has no `Origin`: a page on another site can't send either without a CORS preflight, which the UI never answers (`OPTIONS` is 405), and it authenticates with the header, not a cookie the browser would add. With an `Origin`, it has to be the UI's own. The login's media type is checked without its parameters, which a cross-site page may set.
- **Guessing.** `/api/login` counts failures with `/login`'s, against the name and the address (`login-failed` rows, now with their source), and answers 429 past the limit.
- **Only over TLS.** `--remote` and `morca login` refuse plain `http` but to `127.0.0.1`, `localhost` and `[::1]` (the tests), and a URL with a path, query or user in it; a bare host is `https://`. The client (objectstore's libcurl client) verifies certificates and follows no redirect, so the token can't be sent on to another host, and no `POST` is retried. The token is never in a URL, an argument or a message, and the credentials file is written with mode 600, in a directory made with mode 700, by a new file moved into place under umask 077; one that others can read is refused, as ssh refuses a key.

*Verified* by `tests/remote.sh` (with `tests/test_remote.mojo` for tokens, URLs and the file): over a throwaway Postgres, a user logs in with `morca login http://127.0.0.1:<port>`, backfills, previews, pauses, cancels, resumes, starts and reruns through the UI, and the runs, the pipeline and `orca.audit` change as the local commands change them; bad, expired and revoked tokens get 401, logout revokes, and 5 failures get 429.

PRs 1 to 4 need no AWS account: kind runs on colima on one Mac, and in CI. PR 5 creates paid resources, so its plan (the instance types, the cluster, Postgres, and their cost per month) is agreed before any is created, and what it creates is deleted or kept as agreed when the gate has passed.

### PR 5: on AWS, with the `ec2` runner and with EKS

morca runs on AWS both ways, chosen by `MORCA_RUNNER`. **EKS** (Auto Mode, Karpenter on Spot for runs) is the runner of PR 3 on a managed cluster: autoscaling across nodes, pod identity per run, about $150 a month before a run starts for its control plane and an always-on node. **The `ec2` runner** is for a deployment that can't justify an idle cluster: runs here are batch work, minutes to hours a day, so a small always-on instance holds what has to be up and each run buys instances by the second, for about $60 a month before runs. The `ec2` runner comes first, as the cheaper demo; EKS follows on the same bucket, repository and image.

**`MORCA_RUNNER=ec2`** starts each run on instances of its own, in one Availability Zone (us-east-2a):

1. **A head instance**, on-demand: the run's dista head and its driver (`<binary> resume <run>`, with `DISTA_HEAD` on localhost). `RunInstances` gives back its private address at once.
2. **`workers` worker instances**, Spot when the pipeline is registered with `--spot`, started straight after with `DISTA_HEAD` at the head's address; they wait for the head (`morca.tasks.wait_for_head`) and advertise their own private addresses for results.
3. Each instance starts the pipeline's image from user data and is told to terminate on shutdown, which the script ends with: the head when the driver exits, a worker when its head hangs up and dista's reconnect window passes.
4. **Cleanup in layers, as on Kubernetes:** instances terminate themselves; every tick the scheduler terminates instances tagged `orca.run` whose run isn't running at that start, and those older than the run's deadline; and on start-up it does the same for everything tagged.

A pipeline without dista tasks gets only the head instance. The instance types, the count and Spot are a deployment's choice, so they're given at registration rather than in the pipeline's code: `morca register --image <ecr image> --head-type c7g.large --worker-type c7g.4xlarge --workers 4 --spot <binary>`, defaulting to `MORCA_EC2_HEAD_TYPE`, `MORCA_EC2_WORKER_TYPE` and the pipeline's `workers=`. `--worker-procs N|auto` starts N dista worker processes on each worker instance (auto: one per vCPU), so that a worker that runs one task at a time fills its cores; scaling, the budget and the cost still count instances. `--workers MIN..MAX` scales a run's workers between the two (MIN may be 0): the run starts MIN, and each tick the scheduler reads the head's demand on port 6390 and applies `dista.scale.decide` (over processes, `--worker-procs` per instance), starting workers and draining idle ones with `dista drain`; a drained worker's instance shuts itself down, and `orca.instances` records it as `drained: idle`. `MORCA_VCPU_BUDGET` counts a run's instances' vCPUs before any is started. The image is arm64, so the types are Graviton.

The EC2 API is SigV4-signed HTTPS, as S3 is, so the client is a few calls (`RunInstances`, `DescribeInstances`, `TerminateInstances`, with tags in the call) on objectstore's signing and HTTP; the always-on instance gets its credentials from its instance role (IMDSv2), which objectstore reads already.

**Reaching the UIs.** For the demo they're public: `morca ui` reads without a login and acts only with one (`morca.auth`, rate-limited against guessing before it's exposed), over HTTPS so its cookie is `Secure`, either through a Cloudflare Tunnel (outbound only, nothing open on AWS) or Caddy on the control instance with a Let's Encrypt certificate (ports 80 and 443 open). Logs and errors are public with them, so the demo runs nothing whose logs could hold a secret. LabelControl has no login, so it's public read-only (`LABELCONTROL_READONLY=1`), as its README describes.

**LabelControl** needs two things before it runs there: `linux-aarch64` in its `pixi.toml` (it's built for macOS only today), and a decision about its executor, which runs scene generation, the geometry pass and training in its own process: on the small control instance it would be slow and squeeze everything else, so either it runs elsewhere or its stages become morca pipelines on run instances.

As built in 5a (`morca.ec2`, `morca.awsec2`): the head instance's script runs the head in the background and the driver in front, then keeps the driver's output with `<binary> keep-log`, which appends it to the run's `driver.log` wherever `MORCA_LOGS` is; a worker's script exports `DISTA_ADVERTISE` from `hostname -I`. Instances are told `MORCA_EC2_DATABASE_URL` as their `MORCA_DATABASE_URL`, which goes in their user data: anyone in the account allowed `ec2:DescribeInstanceAttribute` can read it, so the demo's database password is for that database alone. `DescribeInstances` is read without paging, which holds up to a thousand instances. `tests/ec2.sh` (`test-ec2`) is 5a's gate, against `tests/fake_ec2.py`.

**A warm pool** (`morca.ec2`, `morca.pool`; migration 24), added once the census import measured it: its runs did 60–70 s of work each after waiting 30–40 s for a head and workers to boot and join, and EC2 bills at least a minute per start. With `MORCA_EC2_POOL_SECONDS` (150; 0 is the old behaviour), an instance whose run ended waits, idle, for the next run of the same pipeline started as the same instances, and that run takes it rather than launching one. The choices:

- **The key is what the instance was started as**: a digest of its role, type, market, network, profile, the registry hash and its script but for the first run's line (so the image, binary, secrets' IDs, environment and worker processes). The script is the same for every run of a key, which is why it can serve them all.
- **The instance asks Postgres for its next run**, through the pipeline's binary (`pool-next`), every second; it reaches Postgres already, so there's nothing else to run, open or permit (SSM, a port on the instance, S3 polling). The scheduler hands it over by ending its row and inserting the new run's in one transaction, rows locked `FOR UPDATE SKIP LOCKED`, so two starts can't take one instance; `orca.instances` is keyed by instance, run and start, with one live row per instance.
- **A run's reset is a new pass of the script**: a new dista head process (so no task, result or actor carries over), new worker processes, secrets read again, logs and samples named by the new run. A worker learns its run ended from `pool-wait`, since dista workers don't end with their head, and its processes are killed.
- **Liveness before hand-over**: a beat within 5 s and EC2's `running`; one that then doesn't take the run up within 30 s is replaced by new instances, well inside the start grace. Idle instances count against `MORCA_VCPU_BUDGET` and show on `/fleet` as `idle (pooled)`.

*Verified* by `tests/pool.sh`: three runs on one launch, each run's logs its own; another pipeline, a new registration and killed idle instances not reused; the grace; scaling from 1 pooled worker to 3, and the rest left pooled; two runs at once not sharing; a stopped pooled head replaced; the pool off. `tests/ec2.sh` runs with it off.

**Placement** (`morca register --placement control|ec2|default`, `morca.control`; migration 26, #144). The census's small pipelines (mojo_repos, mojo_activity, mojo_stats) used 5–10% of a t4g.medium head and spent most of each 21–45 s run booting it, while the control instance sat at ~4% CPU and ~18% memory (`/system`). A pipeline's *placement* is separate from the scheduler's *runner*: `default` (stored as null) is the runner, as before; `ec2` is instances of its own (on a scheduler whose runner isn't `ec2` its runs wait, `held` with why); `control` is the scheduler's own host.

- **How a control-placed run starts.** As a local run does: the scheduler marks it `running` (`runs.placement = 'control'`) and execs `<binary> resume <run>` as a child, which claims it. On AWS the scheduler runs in a container of the project's image, so the binary is the one the image has (`/opt/morca/pipelines/<p>`, the path `morca aws register` records) and the child runs in the scheduler's container, with its network (`postgres:5432`), `MORCA_WAREHOUSE`, `MORCA_LOGS` and the instance role's credentials. A container per run (`docker run --memory`) was weighed and left out: the scheduler would need the Docker socket, root on the host, which no container has (`tests/aws.sh` checks it); the trade-off is that a scheduler restart (`orca-refresh`, so every `morca aws register`) kills the control-placed runs going, which are then run again as runs whose process died.
- **Limits.** `MORCA_CONTROL_MAX_RUNS` (2) control-placed runs of all pipelines at once, counted under an advisory lock as the vCPU budget is (they count nothing against `MORCA_VCPU_BUDGET`: no instance). Each in a process group of its own at `nice` `MORCA_CONTROL_NICE` (10), so Postgres, the scheduler and the UI win the cores; first for the kernel to kill if memory runs out (`oom_score_adj` 1000, on Linux); and killed by the scheduler once its process tree holds more than `MORCA_CONTROL_MEMORY_MB` (1024) resident (each tick's sample, `morca.sample.tree_usage`; `tree_rss` on macOS), its attempts failed with why. Where the scheduler can make cgroups, each such run also has one at its limit (containment, below), and the sampled cap gives way to it. None starts while the newest minute of `orca.system_minutes` (fresher than 10 minutes) has memory or the fullest disk over 85%. A queued run that waits for a slot or for pressure to pass has the reason in `runs.held`, shown on its page and in its JSON.
- **dista** in such a run is local mode: `MORCA_WORKERS` is `MORCA_CONTROL_WORKERS` (1), forked in its process group.
- **Secrets** are read when the run starts, with `MORCA_SECRET_FETCH` as on instances, else Secrets Manager's `GetSecretValue` over objectstore's SigV4 (the image has no `aws` command; the stack's control role may read `orca/*`), and given to that child's environment alone, named in `MORCA_SECRETS`. Two control-placed runs share a user, so one pipeline's code could read another's environment from `/proc`: placing on the control host trusts its pipelines with each other's secrets, and with the control role (which may start instances), where an EC2 run has the run role.
- **Logs and samples.** The driver's output goes to a staging file (`MORCA_LOG_STAGE/control/`), and once the process is reaped `<binary> keep-log` appends it to `driver.log`, masked, as on an EC2 head; its sampler writes `metrics/control.jsonl`. Attempt logs, timelines, resume, retries, cancel and the stale checks are a local run's: a process that dies is reaped (a crash's attempts failed with its frames), and its run is started again once its heartbeat is stale, within `run_retries`.
- **Where it shows.** The pipeline page, the run page (`Placed`, and `Held` while queued) and their JSON (`placement`, `held`); `/api/fleet` has the control host with the control-placed runs running there (`runs` in `/api/fleet`), sampled or not.
- **Later**: `auto`, placing by past runs' peak memory, CPU and duration.

**Requests and grants** (`cpus`, `memory_gb` in morca.toml, `morca.resources`; migration 36, #171). On one machine shared by every run (the Hetzner server, #166) a hand-set parallelism is wrong again after every rescale, and an `auto` that sizes each run from the whole machine fails as soon as two runs overlap. So a pipeline states a range, `MIN..MAX` of whole CPUs and of GB, and the scheduler hands out the machine:

- **Admission** on the local runner and for control-placed runs, the two that share the scheduler's host. Under an advisory lock (`orcd`, after the control slots' and before the vCPU budget's, so the locks are always taken in one order), the grants of the `running`, not dead, `local` and `control` runs are summed; a start fits if its minimums fit in the host's capacity less `MORCA_RESERVE_CPUS` (1) and `MORCA_RESERVE_MEMORY_MB` (1536) less that sum. The capacity is read once when the scheduler starts: the cgroup's `cpu.max` and `memory.max` (v1's quota and limit too) where lower than the cores and `/proc/meminfo`, `sysctl` on macOS, `MORCA_HOST_CPUS` and `MORCA_HOST_MEMORY_MB` over both. `max_runs`, `fill_max_runs` and the control slots stay caps, checked first. A run that doesn't fit stays `queued` with `runs.held` = `waiting: needs ...`, which the run's page, the pipeline's Progress card (`waiting` in its JSON, the oldest such run's) and the API show.
- **Grants**: greedy, in run order: the first start of a tick takes up to its maximums, the next what that left, until a minimum doesn't fit. A grant is fixed for its start (no shrinking; where cgroups are available it's enforced, below) and given as `MORCA_GRANT_CPUS` and `MORCA_GRANT_MEMORY_MB`; a retry is admitted and granted again. Each start records the request it had and its grant on the run (`request_cpus`, `request_memory_gb`, `grant_cpus`, `grant_memory_mb`); a start without a request writes nulls.
- **Remote workers** admit the same way against their own host: a claim carries `room_cpus` and `room_memory_mb` (capacity less the worker's reserve, 0 and 512 by default), the UI sums the grants of that worker's live runs, and a run that doesn't fit is held saying which worker and left for another; the grant goes to the worker in the run's spec. A claim without a room (an older worker) is answered as before.
- **No request, no change**: such a pipeline takes no lock, is checked against nothing and counted in no sum. That keeps today's behaviour exactly, at the price that a host shared with unrequested runs is only as safe as its reserve.
- **`auto`**: an `env` value is passed as it is, and the pipeline sizes itself from `MORCA_GRANT_*` (`morca.auto_count`, with its own per-unit memory estimate). `DISTA_WORKER_SLOTS`, which dista parses as a number, is resolved by morca: the granted CPUs over the run's local dista workers, or 0 (one per core) without a CPU grant, as on EC2 and Kubernetes. A memory-aware `auto` in dista itself, from each task's estimate, is magmalake/dista.mojo#123; morca then passes `auto` through.
- **Not yet**: requests learned from #200's peaks (`"auto"` requests), requests on EC2 and Kubernetes (sizing their instances and pods), Ops > Control's granted and free amounts, and a request in the pipeline's code (`Pipeline[..., cpus=...]`). A large minimum can wait behind a stream of small runs: there is no reservation for it.

**Containment** (`morca.cgroup`, migration 39, #201). `first_to_go` makes a run's processes the kernel's likeliest victims, but a preference isn't a boundary: on the CAX21 one large run could still take the others down with it. So where it can, `morca scheduler` (and `morca worker`) gives each start a cgroup v2 of its own, `<base>/morca-run-<run>-<start>-<scheduler pid>`, following Borg's per-task limits and Autopilot's raising them after OOMs from history:

- **Where.** `base` is the scheduler's own cgroup (`/proc/self/cgroup`'s `0::` line). cgroup v2 lets a cgroup whose children have controllers hold no processes, so the scheduler first moves what's in it into a leaf `<base>/morca` and writes `+memory` to `<base>/cgroup.subtree_control`; a scheduler already in such a leaf uses the one above. A probe cgroup is made, written and removed. Any step failing turns containment off with one log line saying why (macOS, cgroup v1, a read-only `/sys/fs/cgroup`, no delegated memory controller, `MORCA_CGROUPS=0`), and runs go on as before. Only the scheduler's loop does this: `morca tick` and the other commands reap nothing.
- **Placing the process.** In `morca.proc.spawn`, the parent opens `<cgroup>/cgroup.procs` with `fopen(..., "we")` before `fork`, and the child's first act is `write(fd, "0", 1)`: async-signal-safe, on a descriptor that closes at `exec`. So the run, and everything it forks (dista's local workers), is in the cgroup before its first instruction; the parent moving the pid after `fork` would race the child's own forks.
- **Limits.** `memory.high` is the limit: the start's grant, else its request's maximum, else `MORCA_RUN_MEMORY_MB` (default what the host can grant, `host_room`), at least what an OOM raised the pipeline to; for a control-placed run at most `MORCA_CONTROL_MEMORY_MB`, whose sampled kill then stands aside for it. `memory.max` is `MORCA_RUN_MEMORY_MARGIN` percent (25) above, `memory.oom.group` is 1 (the kernel kills the whole run, not one worker of it), `memory.swap.max` 0. Between the two the kernel throttles the run hard (its penalty grows with the square of the overage, up to 2 s per 256 KiB charged), so a run that keeps allocating there mostly stalls until its heartbeat goes stale: a stale-heartbeat kill of a contained run whose `memory.current` is within 5% of its limit counts as out of memory too.
- **OOM as a failure of its own.** At the reap, `memory.events`' `oom_kill` (or that stall) makes the attempts' error `out of memory at <limit>: ...`, through the same path as the control cap's message (`_exited`, `_crashed`, `interrupt`), not `crashed: killed by signal 9`.
- **Retrying bigger.** The kill sets `orca.pipelines.memory_raised_mb` to the limit times `MORCA_RUN_MEMORY_GROWTH` (1.5), at most the request's maximum (no request: the host's room; control: its cap). Admission raises the request's minimum to it, so the retry, and every later run of the pipeline, waits for and gets at least that; without a request it's the limit's floor. A column on the pipeline rather than a reading of recent attempts: one value admission can use in its query, that outlives the attempts' retention, and that registering a different `memory_gb` resets. It only grows; learning it down from #200's peaks is the `"auto"` requests' job.
- **Recorded.** On the run, its latest start's `memory_limit_mb`, `memory_max_mb` and, every 5 s while it runs, `memory_bytes` (`memory.current`), for Ops > Control; on each attempt, at the reap, the `memory_limit_mb` and `grant_memory_mb` of the start that made it, which the run's Steps table and the attempt page show beside the peak.
- **Cleanup.** At the reap the cgroup's `cgroup.kill` ends what the run left behind, and it's removed, or on a later tick once empty. A scheduler that starts removes the `morca-run-*` cgroups no live process of the named pid made, or that its own pid made before (a container restarted keeps its pid), once they're empty.
- **Workers.** `morca worker` does the same on its host, against its grant, and sends `memory_limit_mb`, `memory_max_mb` and `oom` with `/api/worker/exited`; the UI fails the attempts and raises the pipeline's memory there. Its claim's admission applies the raised minimum too.
- **The Hetzner server** runs the scheduler in a container, whose `/sys/fs/cgroup` docker mounts read-only: `morca-stack apply` gives it its own cgroup namespace and remounts it writable before morca starts, unless `CGROUPS=0` or the host has no cgroup v2 memory controller (docs/hetzner.md#a-cgroup-per-run; on by default since #239). The AWS control instance doesn't yet.

*Verified* by `tests/test_resources.mojo` (parsing, admission, grants, the reasons, `auto`, the host's capacity and reserve) and `tests/grants.sh`: on a made-up host of 4 CPUs and 8 GB, two pipelines whose minimums don't both fit run one after the other, the waiting one held saying why, and with room they run at once; the grants reach each process (`DISTA_WORKER_SLOTS = "auto"` as a number, `auto_count`) and are on the run, its page and its JSON; a pipeline without a request runs as before while another waits for more than the host has; a worker holds a run it has no room for and a bigger one runs it with its grant; `morca config check` refuses bad ranges.

**Admission by memory pressure** (`orca.pressure`, `morca.admission`; migration 40, #202). Requests are estimates: the host can be short of memory while the grants add up (page cache, Postgres, a run past its estimate), and the watchdog reacts only at a fixed usage threshold, by pausing whole pipelines. Pressure stall information is the signal to act on before that, as Meta's TMO does (Weiner et al., ASPLOS 2022): the share of time tasks were stalled waiting for memory, which rises as reclaim and refaults start, well before memory is full. Shedding new work while it's high, and keeping the work already going, is SEDA's admission control under overload (Welsh et al., SOSP 2001).

- **How a start is admitted now**, on the local runner and for control-placed runs: `max_runs` (and `fill_max_runs`) under the pipeline's lock; the control slots and the control instance's newest minute for a control-placed run; then **memory pressure**; then, for a pipeline with a request, the **grants** under the host lock; then the vCPU budget (EC2 and Kubernetes only). Each can only lower how many start, so the order only decides which reason a waiting run shows; pressure comes before the grants so a hold takes no lock. EC2 and Kubernetes runs, on machines of their own, aren't held.
- **The reading.** Each tick reads one PSI file, chosen once when the scheduler starts (`find_source`): `MORCA_MEMORY_PRESSURE_FILE` if set; else the `memory.pressure` of the nearest cgroup, from the scheduler's own (`/proc/self/cgroup`) up, whose `memory.max` is a limit; else the host's `/proc/pressure/memory`; else the own cgroup's though unlimited. In a container `/proc/pressure` is the host's, not the container's, so a container with `--memory` reads its own cgroup, which stalls at its limit even with the host at ease, and one without (the Hetzner stack's) reads the host's, where Postgres and the runs compete. Without PSI (macOS, `psi=0`) nothing changes, said once in the log; a file that stops reading holds nothing, also said once.
- **The rule** (`Admission`, pure, with a monotonic clock): hold while `some avg10` > `MORCA_ADMIT_MEMORY_PRESSURE` (10; 0 is off); release once it's under half the limit, or has stayed at most the limit for 30 s. `avg10` is already an exponential average, and this hysteresis keeps a reading near the limit from starting and holding on alternate ticks. A held run's `held` is `waiting: memory pressure 23% (limit 10%)` (`..., easing` between half the limit and the limit), the same column and `waiting: ` prefix as the grants' reasons, so the run page, the pipeline's **Waiting** and the API show it with no new field.
- **Never forever.** A hold that lasts `MORCA_ADMIT_PRESSURE_GRACE_SECONDS` (600) while none of morca's runs is going on the host can't be waiting for morca's own work to end: it's logged, the `memory-pressure` alert goes once through `morca.notify`, and runs start there one at a time (one only while none is going) until the hold ends. The alert resolves then.
- **Workers** apply the same rule on their own host each poll: a held worker asks for no run (`slots` 0) but still heartbeats, sending its reading (`pressure` in the claim); the UI keeps it and sets the pool's queued runs' `held` to the reason `on worker <name>`, and back to "waiting for a worker" when it eases. The alert for a worker is raised and resolved by the UI from what it sends.
- **Where it shows.** Each host's newest reading is a row of `orca.pressure` (the scheduler's every 5 s and on each change of hold; a worker's on each claim), which Ops › Control (its **Memory pressure** card, `memory_pressure` in `/api/system`), `/api/workers` (for Ops › Pools to show), `/metrics` (`morca_memory_pressure_{some,full}_avg{10,60,300}` and `morca_admission_memory_pressure_held`, by `host`), the home and runs pages' warning and `morca status` read; a row older than a minute is no reading.
- **Runs get the file**: `MORCA_MEMORY_PRESSURE_FILE` (reserved in `env`), so a step can poll it (`morca.memory_pressure`) and lower its own parallelism; dista's adaptive in-flight work (magmalake/dista.mojo#123) is meant to read the same file. The contract is the kernel's format, `some avg10=.. avg60=.. avg300=.. total=..` and a `full` line, read whole; morca adds nothing to it.
- **Kept apart**: `orca.pressure` reads files and decides, with no database, so #201's per-run cgroups can read each run's own `memory.pressure` with it.
- **The watchdog's memory rule stays** the last line of defence.

*Verified* by `tests/test_pressure.mojo` (parsing PSI files and fixtures, `/proc/self/cgroup`, the file chosen for each layout, the hold, its two ways out, off and no reading, and the grace) and `tests/pressure.sh`: with the PSI file a fixture, a run waits at 50% with the reason on its page, the pipeline's, their JSON, the home and runs pages, Control, `/metrics` and `morca status`; still waits at 8%, easing; starts at 1%, its process reading the file; runs start one at a time once a hold outlasts its grace with nothing going, said once; an unreadable file holds nothing; a worker claims nothing while its host's fixture reads 40%, its pool's run saying so, then runs it.

*Verified* by `tests/test_control.mojo` (the values, limits, pressure, environment and secret reading) and `tests/placement.sh`: on the stand-in EC2 with this machine as the control host, a run held by made-up memory and disk minutes, then started; three control-placed runs two at a time with the third held, none starting an instance while a default-placed one does, all listed on `/fleet`'s control host; a secret read from the stand-in Secrets Manager reaching a step and its local tasks with no log holding it; a killed process run again; a run over a 1 MB cap killed with why; and a secret that can't be read failing the start.

### Replacing the control instance

**`morca aws replace-control`** (`morca.aws_replace`; issue #154), added once the census's control instance had drifted from the template: a hand-written Caddyfile (its hostnames), the #142 sampler appended to `orca-refresh` by hand, settings added to `/etc/orca.env` (`MORCA_UI_LINKS`, `DISTA_WORKER_SLOTS`, `MORCA_RUN_ENV`), because any change to the instance's user data made CloudFormation stop and start it, so template changes (#126, #142, #152) were applied by hand or not at all, and none was tested from a fresh boot. Replacing it is now the way such changes land: a new instance from the current template, the old one's database, a health check, then the Elastic IP. The runbook, with the same steps by hand, is `docs/replace-control.md`. The choices:

- **Two slots, not a replacement CloudFormation does.** `Control` (blue, the stack's first, so an existing stack keeps its instance) and `ControlGreen`, each with a condition (`BlueSlot`, `GreenSlot`), and `ActiveControl` naming the one `ControlAddressAssociation` (its own resource) puts the Elastic IP on; a rule refuses an active slot without an instance. A property that forces CloudFormation to replace the instance (a `ControlGeneration` in it) was weighed and left out: CloudFormation would move the address in the same update and terminate the old instance at its end, before any health check, and leave nothing to roll back to. With slots, each step is one update: the new slot on (launch), `ActiveControl` (switch, and back), the old slot off (retire, after `--keep-old`, 24 hours, with the old instance stopped meanwhile).
- **The boot script out of the user data.** It's the user data of `ControlBoot`, a launch template that launches nothing; each slot's own user data is a few lines that fetch its latest version (`ec2:DescribeLaunchTemplateVersions`, on the control role) and run it with the slot's name. Changing the script, or a parameter it reads (`Hostname`, `ConsoleHostname`, `ControlEnv`, `ImageTag`), is a new launch template version and stops no running instance; the next instance runs it. A stack from before the slots has its instance stopped and started once by the update that brings this in (its user data changes), so `morca aws up` refuses that update without `--yes`; `replace-control` makes it while the instance is frozen.
- **Each slot's AMI pinned.** `Ami` is an SSM parameter, which CloudFormation resolves again on every update; a new image id would replace the running instance, and its database with it. `BlueAmi` and `GreenAmi` hold the image each slot's instance has (`morca aws up` and `replace-control` pass them on every update), and a new slot gets the latest.
- **Settings in parameters.** The hostnames are `Hostname` and `ConsoleHostname`; anything else for `/etc/orca.env` is `ControlEnv`, `KEY=VALUE` entries separated by `;`, each replacing the template's line of that key (`--env`, refused for keys that look like secrets, quotes and `;`). The census's are in `docs/replace-control.md`. Secrets stay out: the database password is `DbPassword` (NoEcho), a run's are Secrets Manager's.
- **Dump and restore.** Postgres stays on the root volume; `pg_dump -Fc -n morca` goes to `s3://<bucket>/backups/<stack>/<UTC time>.dump`, is verified by a restore into a scratch database (pipelines, runs, the last run's id, the schema version), and has beside it the image tag, Caddy's data (so the certificates move with the address and Let's Encrypt isn't asked again), the apps (`orca-app` now records them in `/var/lib/orca/apps`; a console started before that is found by its container), the non-secret settings, the hostnames Caddy served and a manifest. `backups/<stack>/restore-<slot>` points the new instance's boot at it, which restores it after Postgres is up and before the scheduler and the UI start. The run role is denied `backups/*`: the dump and the keys aren't for runs. A separate data volume moved between instances would make the copy instant, at the cost of an EBS attach in the swap; later, if the database grows.
- **Quiet, frozen, then copied.** It refuses unless every pipeline is paused and no run is running (`--wait` waits for the runs; it pauses nothing), then stops the old scheduler and UI with restart off (so the stop and start of the first update, or a reboot, doesn't bring them back) and checks again; from here nothing writes to the old database. The UI is down from the freeze to the switch; runs are paused throughout, and stay paused on the new instance until unpaused.
- **Health before the address.** Over SSM on the new instance: the restore was this backup's, the four numbers match (the schema version may be newer), every pipeline paused, the containers running, the UI, `/api/system` and each app answering through Caddy's network, `/system` samples in the last 10 minutes, `morca status`, every setting and hostname the old instance had, and with `--smoke P=KEY` a run of P that succeeds. Then the switch, a check that the address is on the new instance, the old one stopped, and the UI fetched from outside.
- **Rollback both ways.** Before the switch, the new slot off and the old scheduler and UI started again. After it, the new instance holds the newer state, so the rollback is the replacement backwards: quiet, frozen, backed up, restored on the old instance (started again), the address back, the new slot off.
- **Resumable.** Each step is recorded once done in `build/morca-aws/replace-<stack>.state`, and logged with its time in `.log`; `--resume` goes on from the first one that isn't, and `--plan` prints them.

*Verified* by `tests/replace_control.sh`, against the stand-in `aws` (`tests/fake_bin/aws`, which keeps the slots and the address as the parameters deployed set them): the template's slots, boot script, pinned AMIs and denied backups; `up` pinning the AMIs, taking `--env` and refusing secrets and a stack from before the slots; `--plan` doing nothing; refusals while a run is live and while a pipeline isn't paused; `--wait`; the backup (dump, verified restore, pointer), the launch's parameters, the check and the switch in that order; the window; a rollback after the switch and one before it; and retiring the old slot once the window has passed. Not yet run against AWS: the dev-stack rehearsal is the gate for using it on the census.

## Phase 6: getting started

Gate: on a clean machine, an agent given the getting-started page's prompt builds a GitHub Archive lake from 2023 on, imports a day of it every day, sizes its dista workers to the work, and serves a flare app showing how Mojo libraries grew and which Mojo versions they moved to; a person following the page's step-by-step section builds the same thing at a smaller size. Both run on AWS, and the morca UI, the app and the lake's tables stay up afterwards.

The page is written last, from what worked. Writing it is how this phase finds what a user is missing, so the list below is what the first draft found and will grow while the agent runs.

### What the example builds

`magmalake/gharchive.example`, a project of its own made with `pixi shelf add morca`:

1. **`gharchive`**, daily-partitioned (`Daily`, `schedule="0 3 * * *"`, `fills=Previous`): each day's 24 hourly files from data.gharchive.org, read with objectstore's HTTP, parsed as JSON lines and written to `gharchive.events` (Iceberg, partitioned by day). Backfilled from 2023-01-01, a few TB of input.
2. **`mojo_repos`**, a sensor on `gharchive.events`: finds Mojo repositories in each day's events and in GitHub's code search (files ending `.mojo` or `.🔥`, and `pixi.toml`/`mojoproject.toml` naming a Mojo package), and adds the new ones to `mojo.repos`. How repositories are found is the example's code, so the page shows it rather than morca hiding it.
3. **`mojo_history`**, keyed by repository (`Keyed["mojo.repos", "repo"]`, `keys_per_run=50`, `sensor=True`): clones each repository as a dista task, reads its history and writes `mojo.commits` and `mojo.migrations`. New repositories start runs by themselves; a daily refresh brings known ones up to date.
4. **The console**, a flare app reading the `mojo.*` tables: libraries by size and age, Mojo versions adopted over time, and a page per repository.

**The lake's schema.** Everything from GitHub is kept, so questions other than the console's can be asked of it:

| Table | One row per | Columns |
|---|---|---|
| `gharchive.events` | GitHub event | `id`, `type`, `created_at`, `repo`, `actor`, `payload` (JSON) |
| `mojo.repos` | repository | `repo`, `created_at` (GitHub's), `first_mojo_commit`, `first_seen` (first event), `found_by`, `stars`, `forks`, `license`, `default_branch`, `archived`, `description`, `refreshed_at` |
| `mojo.commits` | commit on the default branch | `repo`, `sha`, `committed_at`, `author`, `mojo_files`, `mojo_lines`, `lines_added`, `lines_removed`, `tooling`, `manifest`, `mojo_package`, `mojo_constraint`, `mojo_version`, `channel` |
| `mojo.migrations` | change of tooling or Mojo version | `repo`, `sha`, `at`, `kind` (`tooling` or `mojo`), `from`, `to` |
| `mojo.daily` | repository and day it changed | `repo`, `day`, `mojo_lines`, `mojo_version`, `tooling`, `stars`, for the console's charts |

How the history is read, cheaply: `git log --numstat` over the default branch gives every commit's lines added and removed by file, summed into `mojo_lines` without checking anything out. Only commits touching a manifest or lock file are read with `git show <sha>:<file>`, which is where the tooling and the Mojo version change.

- **`tooling`** is what the project was built with at that commit: `none` (early 2023, the `modular` CLI, no project file), `magic` (`mojoproject.toml`, `magic.lock`), or `pixi` (`pixi.toml`, `pixi.lock`, or `[tool.pixi]` in `pyproject.toml`). A repository's move from magic to pixi is a `tooling` row of `mojo.migrations`.
- **`mojo_version`** is the version the lock file resolved (the `max`, `mojo`, `mojo-compiler` or `modular` package, whichever the project used, kept in `mojo_package`), else the manifest's constraint (`mojo_constraint`), else null. `channel` is `stable` or `nightly`, from the version (`.dev` builds) and the channel URL. Versions are compared in one order across the renumbering (24.x, 25.x, 0.25.x and 0.26.x, 1.x), which the example's code defines and tests.

### The data is public

The `mojo.*` and `gharchive.*` tables are written to a bucket of their own (`mlake-public-<account>`); morca's bucket, with logs and run state, is separate. The lake's bucket is private by default: the instances read and write it with their roles. With the stack parameter `PublicData=true`, a bucket policy lets anyone `s3:GetObject` and `s3:ListBucket`; the project's resource control policy denies S3 to principals of other accounts, so readers read unsigned (`aws s3 ls --no-sign-request`, DuckDB's and pyiceberg's anonymous settings). Downloads are then billed to the project at S3's egress price, with only the Budgets alert as a guard; a mirror with free egress that speaks the S3 API (Cloudflare R2), which Iceberg's `s3://` paths can be pointed at with an endpoint override, is the better way to share the lake than CloudFront, whose https URLs Iceberg readers don't follow.

## Answers proposed to the vision's open questions

| Question | Proposed | Why |
|---|---|---|
| How a DAG is declared | Compile-time, `Step` and `Pipeline` types | It's the only way an edge's types are checked by the compiler, and it's what dista does. Composition comes from pipelines sharing step declarations from a module. |
| Where step code runs | In the pipeline's own binary, as the run's dista driver and workers; the scheduler is a separate generic binary | The scheduler links no pipeline's dependencies, and runs survive a scheduler restart. |
| The UI's stack | Server-rendered HTML from flare, a little JavaScript, JSON at the same paths | One process, nothing to build, API and UI from the same handlers. |
| Cluster start time | Local runtime per run until phase 5, then measure; warm pool only if needed | Measured on the census import: a day's work took 60–70 s and its cluster 30–40 s to boot and join, so the `ec2` runner has a warm pool (`MORCA_EC2_POOL_SECONDS`, 150 s), below. |
| Restate | Not needed: runs are processes that record their own progress in Postgres, and the scheduler is restartable from Postgres alone | Revisit if morca grows long-lived workflows. |
